## 1. 确认顺序

先不要一次性定所有稿。建议按下面顺序逐个确认：

1. 主定位句：一句话说清「我是谁」。
2. 1 分钟中文自我介绍：B2B AI / Digital Twin 版。
3. 1 分钟中文自我介绍：Solution Product / GTM 版。
4. 1 分钟英文自我介绍。
5. Inspector / 设施运维 Agent：20 秒产品定义、90 秒项目经历、2 分钟追问版。
6. Designer / 日本 POC：90 秒版本。
7. 「我到底负责什么产品」45 秒版本。
8. 「为什么换工作」45 秒版本。

## 2. 不可越界事实

| 口径 | 可以说 | 不要说 |
|---|---|---|
| AI Agent | 产品侧方案验证、Demo/POC、可交付规划；你负责业务流、知识源、Agent 边界、输出结构、人审、验收方式 | 不说自己负责底层模型训练；不说已拿到长期采纳率/处理时长等完整运营数据 |
| 设施运维产品 | 运营商私有化部署/实施、香港客户阶段性交付/演示推进、约 5 家客户意向接洽 | 不说大规模正式运营，不把所有商业结果归因到 AI Agent 单点功能 |
| 标品化 | 约 70% 定制诉求向标品转化，属于产品化复盘口径 | 不说是财务口径，不说全部是个人独立贡献 |
| 交付效率 | 某运营商多期项目实施周期从 5-6 个月压缩到 1-2 个月 | 不包装成 C 端留存、DAU 或增长指标 |
| 售前/GTM | 10+ 方案/POC/产品材料；演示视频、培训、市场文案审核、卖点筛选 | 不说自己独立负责销售签约、最终定价或收入指标 |
| Designer POC | 日本头部建工 POC，异形构件堆放/卡车装运，碰撞、限高、载重、重力模拟，后续转正式合同 | 不把合同结果全部归因到个人；客户名按保密口径处理 |

## 3. 自我介绍三点模块库

自我介绍不要固定背一整篇，而是使用「万能开头 + 岗位相关三点」拼装。

万能开头已确认：

> 面试官您好，我是李沛宣。我现在在 DataMesh 做 B 端产品经理，主要做数字孪生、设施运维和 AI 产品化相关的产品。

转场句已确认：

> 如果结合这个岗位来看，我觉得我过去经历里有三块是比较相关的。

### 默认三点

1. AI 产品化 / Agent 任务闭环
2. B 端复杂场景拆解与标品沉淀
3. 方案、售前、交付协同

### 模块分层

| 层级 | 模块 | 使用方式 |
|---|---|---|
| P0 默认必备 | AI 产品化 / Agent 任务闭环 | AI 产品、Agent、B 端智能化岗位优先使用 |
| P0 默认必备 | 复杂 B 端业务拆解 | 通用 B 端、行业产品、平台产品、数字孪生岗位优先使用 |
| P0 默认必备 | 项目需求转标品 / 产品沉淀 | 平台产品、解决方案产品、央国企/运营商、B2B SaaS 使用 |
| P0 默认必备 | 方案 / 售前 / GTM 协同 | 解决方案、GTM、商业化产品、售前产品使用 |
| P1 通用加分 | 跨团队推进 / 研发协作 | 技术产品、复杂项目、产研协作重的岗位使用 |
| P1 通用加分 | 验证与验收意识 | AI 产品、B 端产品、解决方案岗位都可使用 |
| P2 按岗位启用 | 行业学习与迁移能力 | 跨行业岗位，如法律 AI、私域、海外工具、C 端业务岗位使用 |
| P2 按岗位启用 | 英文 / 海外 / 跨文化表达 | 海外产品、外企、英文协作岗位使用 |

说明：

- 「用户视角 / 一线任务理解」并入「复杂 B 端业务拆解」：从一线用户任务开始拆，再进入业务对象、流程状态、字段、权限和异常分支。
- 「MVP 与优先级判断」并入「项目需求转标品 / 产品沉淀」：判断哪些进 MVP，哪些沉淀成标品/配置项，哪些留在客户定制或后续版本。
- 「验证与指标意识」改成「验证与验收意识」：先讲 Demo、POC、场景脚本、验收 case、客户和交付反馈；后续指标只作为继续跟踪的建议，不冒充已拿到完整线上数据。

### 单模块短回答

每个模块控制在 10-15 秒。正式自我介绍时，从下面选 3 个模块拼接，整体控制在 1 分钟左右。

#### 1. AI 产品化 / Agent 任务闭环

我做 AI 产品时，会把它放回真实业务流程里。比如 Inspector 里，我把告警、设备、SOP、历史工单、诊断建议、工单草稿和人工确认串起来，重点定义 AI 需要什么上下文、输出什么结构、哪些结果必须人审。

#### 2. 复杂 B 端业务拆解

我做复杂 B 端产品时，会先看一线用户在什么场景下打开产品、要完成什么任务、哪里会卡住，再拆成业务对象、流程状态、字段、权限和异常分支。设施运维里的告警、设备、空间、工单和 SOP，就是按这个方式拆出来的。

#### 3. 项目需求转标品 / 产品沉淀

面对单个客户的定制需求，我会判断哪些是跨客户共性能力，哪些适合做配置项或行业基线，哪些应该留在项目定制里。过去团队也把约 70% 定制诉求转向标品化，运营商类项目实施周期从 5-6 个月缩到 1-2 个月。

#### 4. 方案 / 售前 / GTM 协同

我也比较熟悉产品和客户之间的翻译工作。过去参与过 10+ 方案、POC、演示材料、培训和市场文案，把产品能力讲成客户能理解的场景价值，同时和售前、交付、研发对齐边界，避免前端承诺和后端实现脱节。

#### 5. 跨团队推进 / 研发协作

我和研发协作时，会尽量把模糊需求拆成具体的流程、字段、状态、原型和验收标准。比如 AI 工单草稿，我会先拆清楚哪些字段来自告警和台账，哪些由 AI 辅助生成，哪些必须人工确认。

#### 6. 验证与验收意识

我过去很多项目是在 Demo、POC 或交付验证阶段，所以会先看关键流程能不能跑通、客户和交付是否认可范围、验收 case 是否通过。后续如果进入真实使用，再继续看采纳率、人工修改原因、处理时长和一次解决率这些指标。

#### 7. 行业学习与迁移能力

进入一个新行业时，我通常先拆用户任务、业务流程、关键数据、专家规则和验收标准，再判断原有经验能迁移到哪里。这样我可以把设施运维和数字孪生里积累的复杂场景拆解方法，迁移到法律 AI、私域运营或海外工具类产品里。

#### 8. 英文 / 海外 / 跨文化表达

我有 UCL 的海外学习背景，也参与过海外客户、英文资料和产品方案相关工作。面对海外或英文协作场景时，我会更注意把复杂功能讲成清楚的用户任务、使用路径和客户价值，减少只堆产品术语的表达。

### 岗位组合建议

| 岗位方向 | 推荐三点 |
|---|---|
| 通用 B 端产品 JD | 复杂 B 端业务拆解；项目需求转标品 / 产品沉淀；跨团队推进 / 验证与验收 |
| AI 产品 / Agent JD | AI 产品化 / Agent 任务闭环；复杂 B 端业务拆解；验证与验收意识 |
| 解决方案 / GTM JD | 方案 / 售前 / GTM 协同；项目需求转标品 / 产品沉淀；客户/交付边界对齐 |
| 跨行业 / 新行业 JD | 行业学习与迁移能力；复杂 B 端业务拆解；验证与验收意识 |
| 海外 / 英文协作 JD | 英文 / 海外 / 跨文化表达；AI 产品化或复杂 B 端业务拆解；方案 / 售前 / GTM 协同 |

## 5. 自我介绍候选稿 1：B2B AI / Digital Twin 版

### 60 秒中文

面试官您好，我是李沛宣，目前在 DataMesh 做 B 端产品经理，主要负责数字孪生、设施运维和 AI 产品化方向。

我和 AI 产品岗位最相关的能力，是把 AI 从一个概念拆成真实业务里的任务闭环。比如在 Inspector 设施运维 Agent 项目里，我不是只做一个 AI 聊天入口，而是把告警、设备台账、空间位置、SOP、历史工单、诊断建议、工单草稿、人工确认和结果回写串起来，并定义每一步的输入、输出、边界和验收方式。

我比较擅长在不确定场景里先把问题拆清楚：用户到底要完成什么任务，AI 需要哪些上下文，输出结果怎么证明可信，什么情况下必须人工确认，bad case 怎么反馈给研发继续调优。

所以如果用一句话总结，我不是单纯写功能需求，而是能把复杂 B 端场景、AI Agent 能力、产品边界和交付验收连成闭环的人。

### 需要你确认

- 「目前在 DataMesh 做 B 端产品经理」是否需要改成更具体的 title？
- 「Inspector 设施运维 Agent 项目」这个叫法你面试时是否自然？还是更习惯说「设施运维 AI 告警诊断」？
- 这版是否应该提前放入「约 70% 定制转标品」这个数字？我的建议：AI 岗先不放，避免 60 秒过载。

## 6. 自我介绍候选稿 2：Solution Product / GTM 版

### 60 秒中文

面试官您好，我是李沛宣，目前在 DataMesh 做 B 端产品经理，主要负责数字孪生、设施运维和 AI 产品化相关方向。

我和解决方案产品岗位最匹配的不是单点 PRD，而是三件事。第一，我做过设施运维产品从项目需求到标品闭环的规划，产品已经进入运营商私有化部署/实施，也有香港客户阶段性推进和约 5 家客户意向接洽。第二，我做过项目需求转标品，会判断哪些是客户偏好、哪些是跨客户共性能力、哪些和产品定位冲突，过去有约 70% 定制诉求沉淀为标准能力或配置项。第三，我也参与过 POC 方案、演示材料、培训、市场文案和售前支持，能把产品能力翻译成客户价值和交付边界。

所以我下一段想做的，是产品和解决方案之间的桥：把前端客户需求讲清楚，把产品能力包装成可复用方案，再和产研一起沉淀到平台能力和 Roadmap。

### 需要你确认

- 「运营商私有化部署/实施」是否可以作为稳定公开口径？
- 「香港客户阶段性推进」是否要改得更保守，例如「海外客户阶段性交付/演示推进」？
- 「约 5 家客户意向接洽」是否可以在非中电信面试中也讲？

## 7. 英文自我介绍候选稿

### 60 秒英文

Hi, I am Jane. I am currently a B2B product manager at DataMesh, focusing on digital twin, facility operations, and AI productization.

My core strength is turning complex real-world workflows into clear and testable product solutions. For example, in an AI facility-operations project, I did not treat AI as a standalone chatbot. I broke down the workflow from alarm detection, equipment context, SOP and historical work-order retrieval, diagnostic suggestions, work-order draft, human confirmation, to result writeback.

In that process, I focused on what context the AI needs, what output structure it should follow, where human review is required, and how the result can be validated by engineering, delivery teams, and customers.

So I would describe myself as a product manager who can connect complex B2B scenarios, AI agent capabilities, cross-functional delivery, and customer-facing value.

### 需要你确认

- 英文名继续用 Jane 是否符合你最近面试习惯？
- 这版偏 AI 产品。如果面试 TruckerPath 这类 C 端岗位，应另做一个「workflow / user-facing product」版本，减少设施运维术语。

## 8. 本轮我的建议
