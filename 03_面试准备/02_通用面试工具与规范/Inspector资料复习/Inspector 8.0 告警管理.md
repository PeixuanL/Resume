## 1 产品设计要点

1. **集中监控与智能筛选**：在统一看板中集中展示所有告警，支持按级别、时间、设备一键筛选和排序，帮助用户从海量信息中快速锁定关键问题。
2. **可视定位与影响分析**：告警自动在3D场景中高亮显示，并可一键查看设备关联关系图，直观判断故障位置和影响范围，实现从“看到告警”到“理解问题”的跨越。
3. **一键处置与流程闭环**：提供从告警到工单的一键转化与派发功能，并支持对误报警进行确认关闭，确保每条告警都有明确的状态与处置记录，形成管理闭环。

## 2 迭代目标

打通告警从发现、定位到处置的全流程，实现关键告警的快速响应与闭环管理。

## 3 核心原则

1. **可视定位与影响分析**：告警自动在3D场景中高亮显示，并可一键查看设备关联关系图，直观判断故障位置和影响范围，实现从“看到告警”到“理解问题”的跨越。
2. **集中监控与智能筛选**：在统一看板中集中展示所有告警，支持按级别、时间、设备一键筛选和排序，帮助用户从海量信息中快速锁定关键问题。
3. **一键处置与流程闭环**：提供从告警到工单的一键转化与派发功能，并支持对误报警进行确认关闭，确保每条告警都有明确的状态与处置记录，形成管理闭环。

## 4. 客户场景描述

### 👨‍💼 角色一：设施运维经理 (张工)
**核心诉求**：建立设备全息档案、变被动维修为主动预防、优化运维资源

#### 4.1.1 场景1：实时监控告警，快速定位并分派关键故障
*   **痛点**：告警信息分散在多个系统中，无法快速识别关键设备故障，导致响应延迟，影响整体运维效率。
*   **场景**：
    1.  张工在3D场景中查看告警信息，系统自动高亮显示触发告警的“冷水机组”，并**弹出告警详情**（设备名称、所在楼层、告警类型：温度传感器超阈值）。
    2.  他点击高亮设备，查看**设备关联关系**，通过连线显示其上下游的泵阀和管道，快速识别故障影响范围（如影响整层空调供应）。
    3.  他立即通过**告警生成工单**，自动创建维修工单，并基于位置就近规则分派给维修工程师小李，同时设置工单超时告警。
*   **价值**：告警响应时间从小时级缩短至分钟级，减少设备停机时间，提升运维协同效率。

#### 4.1.2 场景2：晨会前快速巡检，通过告警列表排序当日工作重点
*   **痛点**：每天上班第一件事就是被各种电话和微信轰炸，不清楚一夜之间发生了哪些告警，哪些紧急，哪些可以暂缓，工作安排混乱。
*   **场景**：
    1.  张工登录系统后，直接进入“告警管理”模块。首页的告警总览Widget显示：当前有**12条未处理告警**，其中紧急**2条**，重要**8条**，警告**2条**。一个简单的饼图直观展示了告警级别分布。
    2.  他点击进入**告警列表**页，列表清晰地展示了每条告警的“触发时间”、“设备名称”、“所在楼层”、“告警标题”、“级别”和“当前状态（未确认/已确认/已关闭）”。
    3.  他使用**时间筛选器**，选择“最近12小时”，并按“告警级别”降序排列。两条标红的“紧急”告警排在顶端：一条是“3F数据中心精密空调高温告警”，另一条是“B1层生活水泵漏水传感器告警”。他迅速确认了这两条告警，并立即执行“生成工单”操作，系统自动填充了设备信息和告警详情，他补充了优先级的备注后分派给相应的维修班组。
*   **价值**：5分钟内从海量信息中锁定最关键任务，变被动响应为主动调度，确保核心业务不受影响。

#### 4.1.3 场景3：人工确认并处理误报警，提升系统可信度与团队效率
*   **痛点**：传感器偶尔误报或因临时性波动触发告警，如果一律生成工单，会浪费维修团队精力，降低大家对告警系统的信任度。
*   **场景**：
    1.  张工在巡检告警列表时，注意到一条“5F办公区CO₂浓度瞬时超标”的告警。他点击该条告警查看详情，历史曲线显示浓度在几分钟内已恢复正常。
    2.  他查看该区域的工单系统，发现当时并无大型会议预约。他结合自己的经验判断，这可能是一次偶然的传感器波动或短暂人员聚集所致。
    3.  于是，他选中该条告警，点击“**人工确认**”按钮，在弹窗中**选择处置方式为“关闭”**，并在备注中填写：“**经核实为瞬时波动，环境参数已恢复正常，属误报警。**” 这条告警将被关闭，并记录在案供后续审计，但不会产生不必要的工单。
*   **价值**：过滤噪音，确保工单系统处理的是真实问题，维护了告警系统的严肃性，让维修团队专注于真实故障。

### 👔 角色二：高层领导 (王总)
**核心诉求**：洞察运维绩效、保障业务连续性、优化成本投入

#### 4.2.1 场景4：通过告警仪表盘，宏观把脉设施健康度
*   **痛点**：无法快速、直观地了解整个设施群的运行稳定性和运维团队的工作负荷，听汇报时只有抽象数字，缺乏感知。
*   **场景**：
    1.  王总打开数据大屏，首页的“告警监控”区域非常醒目。一个大的数字显示“**本月平均告警响应时长：25分钟**”，旁边是“**本周告警总数趋势图**”，可以看到周一到周四呈下降曲线。
    2.  他点击图表钻取到告警列表页，看到一个“**告警TOP5设备类型**”的排行榜，发现“水泵”类设备名列前茅。他吩咐助理：“把这个问题列入下周管理会议程，我们需要分析一下水泵的共性问题。”
*   **价值**：一分钟掌握运维核心KPI，用数据驱动管理决策，发现问题苗头。

#### 4.2.2 场景5：审阅月度运维报告，基于告警数据决策预算
*   **痛点**：审批运维预算和设备更新计划时，缺乏量化的数据支撑，难以判断其合理性和紧迫性。
*   **场景**：
    1.  王总审阅张工提交的《月度运维报告》。报告中重点引用了告警系统的数据：“**B栋冷冻机组上月共产生15次‘油压过低’告警，同比上升300%，MTBF（平均无故障时间）已低于标准值。**”
    2.  报告附带了从告警列表导出的该设备历史告警清单和趋势图，证据确凿。基于此，张工提出了“对B栋冷冻机组进行预防性大修”的预算申请。
    3.  王总看到清晰的数据关联，迅速批准了该预算，因为他知道这避免了未来可能发生的灾难性故障。
*   **价值**：让每一笔运维和投资预算都**有据可依**，实现从“成本中心”到“价值投资”的视角转变。

#### 4.2.3 场景6：确保合规性，应对审计检查
*   **痛点**：面对Green Mark等绿色建筑认证或内部审计时，需要证明对关键设施（如消防、空调）进行了有效监控和管理，手动整理记录耗时且易出错。
*   **场景**：
    1.  审计方要求提供“过去一年内所有消防水泵的故障与处置记录”。王总让张工直接从**告警管理模块**输出报告。
    2.  张工使用告警列表的筛选和导出功能，快速生成了包含“触发时间、设备名称、告警详情、处置人、关闭时间”的标准化报告。
    3.  报告清晰显示了每一次告警都得到了及时确认和处置，形成了完美的**闭环证据链**。王总自信的将报告提交给审计方。
*   **价值**：告警系统成为**合规性的自动化基石**，轻松应对审计，提升企业风险管理能力。

## 9.A 数据设计

**数据接入:**
对应客户业务系统（告警系统或IoT业务数据），在数据接入时建立映射表，将客户系统中的告警字段与DataMesh告警管理中的固定字段（告警名称、告警对象、告警类型、告警等级、告警时间、持续时间、告警ID、告警描述等）进行对应，如告警点位ID与空间/设备孪生体ID进行对应

其中告警位置以该空间孪生体的位置/告警关联设备的资产管理-设备位置显示，告警状态以系统内的告警状态变更显示

<span style="color:red">若缺少某些属性值，则对应位置显示为【-】空</span>

*   Inspector运维助手首页-左侧点击【告警管理】按钮-告警管理首页-点击列表某一行-告警详情

<span style="color:red">运维助手段不可进行告警处置</span>

**B.页面数据**

**B1.基础信息**

| | 字段名称 | 数据来源 | 描述 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 告警对象 | 系统 | 告警详情页「告警对象」字段内容<br><br>优化项：若为设备，后续可通过点击设备名称，打开设备详情页 | 第一次触发的告警空间/设备（应和后续告警一致） |
| 2 | 告警位置 | 系统 | | 第一次触发的空间/设备位置（应和后续告警一致） |
| 3 | 告警名称 | 系统 | | 随合并的最新告警更新 |
| 4 | 来源系统 | 系统 | | 第一次触发的来源系统（应和后续告警一致） |
| 5 | 告警等级 | 系统 | | 随合并的最新告警更新 |
| 6 | 告警类型 | 系统 | | 第一次触发的告警类型（应和后续告警一致） |
| 7 | 告警状态 | 系统 | | 系统中记录的状态变更 |
| 8 | 告警描述 | 系统 | | 第一次触发的告警描述（应和后续告警一致） |
| 9 | 告警时间 | 系统 | | 第一次告警的时间（还需考虑最后一次告警时间） |
| 10 | 持续时长 | 系统 | | 从第一次触发开始计算 |
| 11 | 告警ID | 系统 | | 第一次触发的告警ID |
| 12 | 扩展内容 | | 展示其他客户业务系统中的告警字段 | 随合并的最新告警更新 |

**B2.历史记录**
*   当该条告警触发时，需要记录此时的时间，并在历史记录中记录【触发】类记录，同时告警状态为【未响应】；
*   当该条告警被【运维经理】用户操作「确认」时，在历史记录中记录【确认】类记录；
*   当该条告警被【运维经理】用户操作「关闭」时，在历史记录中记录【关闭】类记录；
*   当该条告警有重复的告警事件合并写入后，在历史记录中记录告警信息更新
