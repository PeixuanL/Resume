## 3. 已确认的故事库状态

### S1 Inspector 设施运维 Agent 闭环

状态：强支撑，可直接讲，但注意边界。

能打：AI Agent 项目、RAG、准确性、验收、人审、没有底层模型经验怎么办。

边界：

- AI Agent 是产品侧方案验证、Demo/POC 和可交付规划。
- 不说模型训练，不说全量上线，不说真实准确率提升。
- AHU-03、张工、78%、52 分钟等示例只能作为产品设计示例，不能说成真实发生。

### S2 项目需求转标品

状态：中强支撑，可讲，仍需确认统计口径。

能打：70% 怎么来、客户强定制怎么办、行业版本怎么沉淀。

当前口径：

- 约 70% 是产品化复盘口径，不是财务口径，不是个人独立贡献口径。
- 需求分三类：客户偏好 -> 配置；跨客户共性 -> 标准模块；产品定位冲突 -> 回到真实痛点给替代方案或边界。
- 可讲结果：某运营商多期交付由 5-6 个月压到 1-2 个月。

### S3 产品上线/推广支持

状态：已形成当前可用答案，后续补复用结果。

真实事实：

- 涉及 Designer 7.4，以及 Designer / Inspector 8.0、8.1 迭代。
- 面向市场团队、项目经理、实施/交付、售前做产品价值传递。
- 做设施运维产品实施流程培训。
- 提供实际软件操作演示视频。
- 帮市场审核公众号宣传文案。
- 筛选卖点标准：市场价值、客户 ROI、过去无法实现的新场景、新增业务能力、完整闭环能力、显著提效交互。
- 简单交互优化、客户感知弱的内容不作为主卖点。

当前可用回答：

> 我过去做过产品迭代后的市场和项目团队赋能。比较典型的是 Designer 7.4，以及 Designer / Inspector 8.0、8.1 这些版本迭代。
> 当时产品能力更新很多，但我不会把功能清单原样交给市场，而是先判断哪些功能真的能转成客户价值。我的筛选标准主要看三点：第一，对客户 ROI 有没有明显帮助；第二，是不是过去无法实现的新场景；第三，能不能形成完整业务闭环。像一些简单交互优化，如果客户感知不强，我不会放到主卖点里；但如果是新增监控视频接入、新增模块、设施运维闭环能力，或者能明显提升项目实施效率的交互，我会重点提炼出来。
> 之后我会面向市场和项目团队做产品价值传递，同时提供实际软件操作演示视频，帮助市场理解真实产品能力。市场基于这些内容写公众号宣传文章时，我也会帮忙审核文案，避免只讲技术词或夸大能力，而是把功能表达成客户能理解的场景价值和实施边界。
> 这段经历让我意识到，产品经理不只是把功能做出来，还要把功能翻译成市场能讲、项目能交付、客户能理解的价值。这一点和中电信这个产品解决方案经理岗位很接近。

渠道/省公司赋能回答：

> 我会先把这件事理解成赋能体系问题，而不是单次培训问题。过去在 Designer 7.4、Designer / Inspector 8.0/8.1 迭代后，我做过类似工作：面向项目经理、实施/交付、售前和市场团队做产品价值传递和设施运维实施流程培训。我的做法不是让大家背功能清单，而是把版本能力拆成几类资产：客户痛点、核心卖点、操作演示视频、实施流程、交付边界和宣传口径。
> 如果迁移到星辰智能体，我也会按这个思路做渠道和省公司赋能：第一，给他们 5 分钟能讲清的价值话术；第二，给标准 Demo 脚本和真实操作路径；第三，给 POC 前置条件和验收样例；第四，给常见异议和边界，比如哪些场景需要私有化、哪些动作必须人审、哪些效果不能夸大。这样渠道不是只会说“大模型很强”，而是能讲清客户为什么需要、怎么试、怎么交付、出了问题怎么兜底。

待补：

- 演示视频/培训材料/公众号是否被复用。
- 项目团队是否减少重复咨询或更清楚实施流程。
- 选一个具体新增闭环能力：迭代前做不到什么，迭代后能完成什么。

### S4 日本头部建工 POC 范围收敛

状态：已从方法论升级为具体 POC 场景，仍缺交付物/验收反馈。

真实事实：

- 客户核心场景：货物堆放、卡车运输异形建筑构件的货物分配。
- 涉及能力：重力模拟、载重、限高测算与超出时识别、货物摆放时的碰撞检测。
- 材料中可讲：某日本头部建工企业 POC 后续转入正式合同。

当前可用回答：

> 我理解 B 端 POC 最怕范围太大，最后什么都试一点，但没有一个闭环能证明价值。之前在日本头部建工企业相关 POC 中，客户核心关注的是异形建筑构件在货物堆放和卡车运输中的分配问题，不是简单看一个 3D 模型。这个场景要验证构件怎么摆放、会不会碰撞、是否超出车辆限高和载重，以及重力和空间关系是否支持合理堆放。
> 所以我会先和售前一起把客户真实痛点收敛成 1 到 2 个可验证场景，而不是把 Designer 的所有能力都演示一遍。然后提前写清数据前置和成功标准：比如需要哪些构件尺寸和车辆约束，验收时看碰撞检测、限高/载重识别、摆放方案是否能支撑客户判断。
> 过程中如果客户新增需求，我不会直接拒绝，而是分成本期必须验证的核心闭环、可以用替代方案覆盖的增强项、以及后续正式交付或二期范围。这样客户感觉需求被承接，但团队不会失去 POC 主线。这个项目后续转入正式合同，我会谨慎表达为：我参与了 POC 范围和成功标准收敛，让试点结果能映射到正式交付范围和里程碑。

待补：

- 原本范围有没有更散？具体砍掉了什么。
- 你产出了什么：方案、验收表、数据前置清单、Demo 脚本、会议纪要。
- 客户最终最认可哪一点：重力模拟、载重/限高、超限识别、碰撞检测，还是整体货物分配方案。

## 4. 当前已记录的问题答案

### Q：没有收入指标，怎么证明商业结果？

当前角度：

- 不硬讲收入归因。
- 讲设施运维产品 / Inspector MVP 覆盖标杆客户 80%+ 高优诉求、吸引 5+ 潜在客户接洽。
- 讲某运营商多期交付 5-6 个月压到 1-2 个月。
- 讲 10+ 方案/POC/产品材料支持。
- 强调这些是产品底座、方案包装、演示材料、交付路径共同作用，不归因为单次公众号或 AI Agent 单点。

可用回答：

> 如果严格说收入归因，我没有独立背过销售收入指标，所以不会把结果说满。但产品解决方案岗的价值不只体现在最终签约，也体现在前链路是否能推动客户理解、售前复用和交付准备。
> 我能讲的事实是，设施运维产品 / Inspector MVP 覆盖了标杆客户 80%+ 高优诉求，并吸引 5+ 潜在客户接洽；某运营商多期交付周期从 5-6 个月压缩到 1-2 个月。这个结果不是单次公众号或 AI Agent 单点功能带来的，而是产品底座、方案包装、演示材料和交付路径共同作用的结果。
> 在这个过程中，我做的贡献主要有三类：第一，把 Designer 7.4、Designer / Inspector 8.0/8.1 的迭代功能按客户 ROI 和市场卖点筛选，提炼成客户能听懂的价值；第二，提供实际软件操作演示视频，并面向项目经理、实施/交付、售前和市场做产品价值传递和设施运维实施流程培训，让材料和口径能被多团队复用；第三，审核市场公众号文案，确保宣传既能突出价值，也不夸大产品边界。
> 所以如果问我怎么证明商业价值，我会说我没有直接收入归因，但我能证明自己参与了从产品能力到客户理解、市场传播、售前复用和交付准备的前链路，这正是产品解决方案经理需要补位的地方。

### Q：商业化定价和竞品分析怎么做？

状态：已有当前答案，偏方法论，缺具体案例。

核心：没有最终拍板价格，但可以提供定价前结构化依据。

四层拆法：

1. 基础产品能力：账号、组织空间、权限、基础模块、标准数据看板、基础 3D 场景或标准工作流。
2. 接入规模：设备、点位、数据源、业务系统、知识库、用户账号、token/API 调用量。
3. 高级能力或行业包：视频接入、告警到工单、SOP 模板、预测性维护、AI 诊断、移动端执行闭环。
4. 实施和服务成本：私有化部署、数据治理、系统接口、权限/审计、培训、运维支持、版本升级。

迁移到星辰智能体：

- SaaS 试用或个人/小团队版。
- 企业团队版。
- 行业方案版。
- 私有化/省专版本。

过去经验防守：

> 我过去没有独立做最终定价，但做过类似的价值和交付拆解。比如在设施运维产品里，我会把能力拆成基础底座、可配置模块、行业/项目场景和实施服务。基础底座包括资产、告警、3D 场景、工单这些通用能力；高级模块包括视频接入、设施运维闭环、AI 辅助诊断这类更强场景价值；实施服务则包括客户数据接入、现场配置、项目团队培训和交付边界确认。
> 这类拆解虽然不是最终报价，但会直接影响售前怎么讲方案、市场怎么包装卖点、项目团队怎么判断交付成本。我的价值是在定价前把客户为什么愿意付费和我们交付成本在哪里拆清楚。
