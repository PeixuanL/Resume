# 中电信人工智能公司二面 Q&A 练习稿

> 版本：2026-07-28
> 岗位：产品解决方案经理 / 星辰智能体 / B 端 AI 方案 / 商业化推广
> 使用方式：先练 Top 8 必练题，再扩展压力追问。回答时始终按“结论 -> 判断框架 -> 真实项目 -> 迁移到中电信”收束。

## 二面总打法

小红书二面经验贴的共同信号是：一面筛“能不能干活”，二面筛“能不能站在负责人视角一起做事”。所以这轮不要只复述项目经历，要主动证明四件事：

1. 我不只是执行功能，而是能判断为什么做、怎么取舍、怎么沉淀。
2. 我能把 AI Agent 从 Demo 讲成可销售、可交付、可验收的产品方案。
3. 我能在研发、售前、渠道、省公司、客户之间搭桥。
4. 我知道自己的短板，但有清晰的 30/60/90 天补齐路径。

一句话主线：

> 我理解这个岗位不是普通 PRD 产品经理，而是在产品、解决方案和商业化之间搭桥，把星辰智能体的平台能力包装成客户听得懂、销售讲得清、渠道能复用、交付能验收的方案。

## Top 8 必练

### 1. 你怎么理解这个岗位到底在招什么人？

**为什么会问**：二面常由部门负责人/业务大 leader 面，考察是否从“执行者视角”升级到“业务负责人视角”。

**我的答案**：

我会把这个岗位理解成 AI Agent 产品解决方案经理，而不是传统只写 PRD 的产品经理。

从一面沟通和 JD 信号看，这个岗位有三层核心要求。第一是能力产品化，把星辰大模型、星辰智能体、知识库、工作流、工具调用、评测、权限这些平台能力，拆成客户能理解的产品版本和场景包。第二是方案商业化，区分 SaaS、企业团队版、行业方案和私有化部署，把产品能力转成定价分层、渠道话术、Demo 和客户方案。第三是推广规模化，不是每个客户都重新定制，而是让售前、渠道、省公司有标准材料、标准演示和反馈闭环。

所以我理解这个岗位真正要招的人，是能在产品、解决方案、GTM 和交付之间搭桥的人。我过去做过 AI Agent 闭环拆解、B 端项目需求标品化、售前方案和 POC 边界对齐，这些经验可以迁移到星辰智能体的产品包装和行业方案沉淀里。

**追问防守**：

如果问“为什么不是普通产品经理”，答：

> 因为这个岗位明显不只要求内部功能规划，还要求产品能力矩阵、版本定价、推广模式、渠道架构、竞品分析和客户方案输出。它更像产品底色的解决方案/GTM 角色。

### 2. 请做一个 90 秒自我介绍，重点贴合二面

**为什么会问**：小红书经验里，二面很怕候选人还停留在“我做过什么”。开场要先给岗位匹配结论。

**我的答案**：

面试官您好，我是李沛宣，目前在 DataMesh 做 B 端产品经理，主要负责数字孪生、设施运维和 AI 产品化方向。

如果结合贵司这个岗位，我觉得自己最匹配的不是单点产品经验，而是三类能力的组合。

第一是 AI Agent 产品化能力。过去在 Inspector 设施运维 Agent 项目里，我不是把 AI 做成一个开放式聊天框，而是把告警、设备台账、空间位置、SOP、历史工单、诊断建议、工单草稿、人工确认和结果回写串成闭环，并定义每一步的输入输出、知识源优先级、人审边界和验收口径。

第二是 B 端产品包装和标品化能力。客户需求一开始经常很散，我会拆成用户任务、业务对象、流程状态和配置项，再判断哪些是客户偏好、哪些是跨客户共性、哪些和产品定位冲突。过去我推动过约 70% 定制诉求向标准能力、配置项或模板沉淀。

第三是商业化协同能力。我不是只在内部写 PRD，也参与过 10+ 项目的客户需求澄清、POC 范围收敛、方案材料、演示内容和交付验收口径对齐。

所以我理解自己和这个岗位的匹配点，是能把复杂 AI 或 B 端产品能力，转成客户听得懂、销售能讲清、研发能实现、交付能验收的产品方案。

### 3. 讲一个你做 AI Agent 或 AI 产品化最有代表性的项目

**为什么会问**：二面会追“怎么证明成果是你带来的”“为什么这样设计”，不是只听项目介绍。

**我的答案**：

我会讲 Inspector 设施运维 Agent 项目。这个项目的背景是，楼宇或园区运维里，一线人员看到告警以后，真正困难不是“知道有告警”，而是要判断影响哪个设备、在哪里、原因可能是什么、下一步查什么、是否需要生成工单，以及处理结果怎么沉淀。

我在里面做的核心不是底层模型训练，而是把业务流拆成 Agent 产品闭环。第一，我拆知识源：实时告警和传感器状态用于判断当前发生了什么；设备台账和空间位置用于确认对象是谁、在哪里；SOP 和厂商手册作为标准依据；历史工单只能作为类似经验参考。第二，我拆 Agent 职责：告警理解负责结构化原始告警，RAG 负责召回 SOP、历史工单和设备资料，诊断 Agent 输出可能原因、依据和置信度，方案 Agent 给建议检查项，工单 Agent 只生成草稿，不自动派发。第三，我定义输出结构：可能原因、判断依据、置信度、缺失信息、建议动作和人工确认标记。第四，我和研发、测试对齐验收脚本，比如某个楼层空调机组温度异常，应该召回哪类 SOP，不能召回哪些跨设备、跨楼层资料。

这个项目我会谨慎表达：AI 部分是产品侧方案验证、Demo/POC 和可交付规划，不包装成大规模上线效果。但它证明了我能把一个很虚的“大模型诊断”，拆成研发能做、测试能验、客户能理解、现场人员敢用的产品闭环。

迁移到星辰智能体，就是同样的方法：先拆业务任务和知识源，再拆 Agent 工作流、输出协议、评测口径、人审边界和交付前置条件，最后沉淀成行业模板和方案包。

### 4. 你怎么定义一个智能体产品？怎么验收它不是 Demo？

**为什么会问**：这是你二面 AI 深挖的主防线。负责人会看你是否懂“可交付”和“可信边界”。

**我的答案**：

我不会把智能体定义成聊天机器人，而是定义成围绕业务任务运行的 AI 应用。它至少要有任务目标、用户输入、知识源、工具/API、工作流、输出协议、权限边界、人审节点、失败兜底和评测机制。

验收也不能只看“能不能回答”。我会分六项：第一是场景验收，是否覆盖目标用户的高频任务；第二是知识验收，是否命中正确业务对象、正确知识源、正确版本和有效证据；第三是输出验收，是否按约定结构输出结论、依据、置信度、缺失信息和下一步动作；第四是风险验收，低置信、高风险、跨权限、缺资料时是否触发人审或兜底；第五是业务验收，业务人员是否愿意采纳，人工修改量是否可接受，结果是否能进入下一流程；第六是交付验收，部署环境、数据源、接口、权限、运维责任和培训材料是否齐备。

所以从 Demo 到可验收产品，中间差的是业务闭环、知识治理、权限审计、评测样例、人审机制、运维责任和持续 bad case 迭代。

**追问防守**：

如果问“它和聊天机器人有什么区别”，答：

> 聊天机器人主要完成对话回复，智能体要完成业务任务：理解目标、检索知识、调用工具、推进流程、输出结构化结果，并在必要时触发人工确认。

### 5. RAG 怎么设计？怎么判断召回和回答准确？

**为什么会问**：二面容易从“你懂 Agent 吗”追到产品技术协同。

**我的答案**：

我不会把 RAG 理解成上传一堆文档让模型回答，而是把它当成业务任务里的上下文检索层。

第一步要先分知识源。比如事实类数据、标准类知识和经验类知识不能混在一起。实时告警、设备状态、客户信息属于事实；SOP、制度、产品手册属于标准依据；历史工单和历史案例只能作为类似参考。不同知识源的可信度、更新时间和引用方式不一样。

第二步判断召回准不准，不是只看语义相似度，而是看是否命中正确业务对象、正确任务类型、正确知识源、正确版本和有效证据。错对象、错场景、错版本、越权限，都不能算合格。

第三步判断回答准不准，要看回答是否有依据、是否结构化、是否标注不确定性、是否能说明缺失信息，以及高风险场景是否触发人工确认。

迁移到星辰智能体，我会把这些标准转成平台和方案材料里的评测口径：召回命中正确知识源，回答标注依据，低置信不下确定结论，高风险任务必须人审。这样客户不是只听“我们用了大模型”，而是能看到智能体为什么可信、怎么验收、出问题怎么改。

### 6. 你过去更偏产品，怎么证明你能做 GTM 和商业化推广？

**为什么会问**：这是中电信这轮最大的二面风险。小红书经验也提醒，二面负责人更看“能不能一起把业务推下去”。

**我的答案**：

我不会把 GTM 理解成单纯市场宣传，而是理解成产品能力如何被客户理解、被销售讲清、被渠道复用、被交付验收。

我过去虽然 title 是产品经理，但实际做过售前方案、POC 范围、演示脚本、产品材料、项目培训和反馈沉淀，支持过 10+ 份方案/POC/产品材料。比如产品上线或对外推广时，我不是把二十多个功能全部讲出来，而是和售前、项目、市场侧一起筛出十个真正能打客户痛点的推广点，转成客户价值、Demo 话术和交付边界。

如果迁移到星辰智能体，我会按四步做：客户分层、价值主张、可复用资产、反馈闭环。客户分层要区分个人/小团队、企业部门、政企行业客户、省公司/渠道；价值主张要把模型、RAG、工作流、工具调用、评测翻译成客户能买单的业务结果；可复用资产包括标准 Demo、方案模板、版本矩阵、竞品对比、POC 验收和常见异议；反馈闭环要看销售是否讲得清、客户是否愿意试用、POC 卡在哪里，再反哺产品包装和 Roadmap。

**追问防守**：

如果问“你没有背过收入指标怎么办”，答：

> 我没有独立背过销售收入指标，但我做过影响线索转化和 POC 推进的上游工作，比如产品包装、方案材料、演示脚本和验收边界。入职后我会先对齐团队指标，再把产品侧产出和线索转化、POC 成功率、渠道复用率挂钩。

### 7. 你说约 70% 定制需求转标品，具体怎么判断和落地？

**为什么会问**：二面会追“怎么证明成果是你带来的”。这个问题要讲判断，而不是只讲结果。

**我的答案**：

我会谨慎表达这个数字：约 70% 指的是一批项目需求没有被做成单客户代码，而是沉淀成标准能力、配置项、模板或产品规则。它不是财务口径，也不是收入归因，而是项目需求复盘里的产品化口径。

判断上我分三类。第一类是客户偏好，比如字段显示、入口位置、命名习惯、流程顺序，这类尽量做成配置项或模板。第二类是跨客户共性业务问题，比如资产台账、设备关系、3D 空间定位、告警到工单、SOP 模板、知识库引用、人工审核，这类如果反复出现，就抽象成标准模块。第三类是和产品定位冲突的需求，比如客户希望产品变成一次性脚本或纯项目工具，我会回到真实痛点，用更符合平台架构的方式解决。

落地上，我会让需求从项目交付件变成产品资产：配置项、模板、实施基线、Demo 脚本、交付手册和 Roadmap。这个经验迁移到贵司，就是未来从通用办公智能体进入行业版本时，不能每个省公司、每个客户都做一套，而要把高频场景沉淀成可复制方案包。

### 8. 如果你入职，前 90 天会怎么开展工作？

**为什么会问**：二面负责人会看你是不是只会“表达意愿”，还是能转成实际工作计划。

**我的答案**：

我会分三阶段。

前 30 天先建立产品和市场底图。我会深用星辰智能体平台、TeleAgent、星辰慧记等产品，梳理能力矩阵、版本包装、客户群体、现有渠道材料和典型交付流程；同时拆竞品，比如 Coze、Dify、百度/阿里/腾讯的智能体平台，看它们在应用创建、知识库、工作流、评测、发布、私有化和行业模板上的差异。

31 到 60 天，我会选 1 到 2 个重点客户群体或场景做产品包装优化，比如政企知识问答、办公工作助手、客服辅助或工业/园区场景。输出内容包括产品能力矩阵、版本分层、演示脚本、客户方案模板、竞品对比和 POC 验收口径。

61 到 90 天，我会和研发、销售、渠道、运营一起跑小闭环。不是只交一份 PPT，而是看前端销售是否讲得清、客户是否愿意试用、POC 前置条件是否明确、交付是否接得住，再根据反馈调整版本包装、定价结构、行业模板和产品 Roadmap。

90 天的可见成果，我希望至少是一套场景方案包、一套版本包装建议、一套竞品对比、一套 POC 验收模板，以及一次和销售/渠道共同验证后的反馈闭环。

## 高频压力题

### 9. 你没有通用 AI 平台经验，怎么胜任？

**我的答案**：

我没有在通用 AI 平台完整做过这个岗位，所以不会把自己包装成已经熟悉星辰所有产品矩阵的人。但我有一套可以迁移的方法。

Inspector Agent 项目已经覆盖了 Agent 产品化的关键问题：业务任务怎么拆、知识源怎么分层、RAG 怎么验收、什么输出必须结构化、哪些节点必须人审、bad case 怎么沉淀。平台层面我需要补的是产品矩阵、客户分层、渠道打法和现有定价策略。

我的补齐方式会很具体：先深用产品和现有方案，跟销售/交付复盘典型项目，再选一个场景做方案包小闭环。我的优势不是只“学习快”，而是能把学习结果变成可复用的产品材料、演示脚本和验收标准。

### 10. 你没有独立负责定价，怎么做产品包装和定价？

**我的答案**：

我没有独立拍板过最终价格，这个我会如实说明。但产品经理在定价前链路里仍然可以提供结构化依据。

我会先拆客户分层和价值差异。比如个人/小团队更关心低门槛试用和标准模板；企业团队更关心协作、权限、用量、团队空间和管理；行业客户更关心行业模板、知识治理、验收样例和服务支持；私有化客户更关心内网部署、数据不出域、权限审计、系统对接和运维责任。

定价组成上，我不会拍一个具体数字，而会拆成平台订阅、资源消耗、行业模板包、私有化部署服务、二次集成和持续运营几部分。这样销售可以按客户预算组合，交付也知道边界在哪里。

### 11. 渠道和省公司不会讲智能体怎么办？

**我的答案**：

我会先承认这个问题很真实。智能体如果只讲“大模型很强”，渠道和省公司很难卖，也很难交付。

我的做法是做一套标准工具包，而不是只做培训会。里面至少包括：目标客户痛点、适用行业、5 分钟 Demo 脚本、典型场景话术、竞品差异、部署前置条件、价格组成、POC 验收口径、常见异议和成功案例。

同时要做反馈闭环。比如销售讲不清的是功能价值、价格组成、交付边界，还是客户不信效果？每类问题要回到不同资产：话术、方案模板、演示脚本、产品能力或 Roadmap。这样渠道不是一次性被培训，而是逐步形成可复制的销售和交付机制。

### 12. 客户说智能体回答不稳定、不可信，你怎么排查？

**我的答案**：

我不会直接归因成“模型不行”，而会按链路拆 bad case。

第一类是知识缺失，知识库本来没有正确答案；第二类是文档切片或标签问题，资料有但模型找不到；第三类是检索问题，召回了相似但错误的对象、版本或场景；第四类是生成问题，召回正确但回答时扩大解释、遗漏依据或没有标注不确定性；第五类是产品边界问题，本来就不应该让智能体直接下结论，而应该触发人工确认。

排查后要对应动作：补知识、调切片、补元数据、加过滤条件、调整 rerank、收紧输出结构、设置低置信兜底和人审规则。

放到星辰智能体平台，我会把这些 bad case 不只当成单次修复，而是沉淀成评测集、行业模板、知识库治理规范和客户交付验收表。平台不是承诺永远不出错，而是有发现、定位、修复和持续运营机制。

### 13. 你讲的数字偏过程，怎么证明真实业务结果？

**我的答案**：

我会先承认边界：我不会把没有上线口径的数据包装成业务结果。

已确认的结果我会讲事实数字，比如入职后快速接手两条产品线、第二周参与演示、一个月梳理 MVP、约 70% 定制需求沉淀为标品、支持 10+ 份方案/POC/产品材料、从二十多个功能里筛出十个推广点。

这些数字确实有一部分是过程指标，但它们证明的是这个岗位需要的上游能力：快速进入复杂产品、把项目需求变成标准能力、把功能翻译成客户价值、支持售前和推广闭环。

如果面试官问 AI Agent 的业务效果，我会把它定义成验收指标，而不是虚构上线结果。比如正确召回率、样例问题通过率、人工修改量、结果采纳率、平均处理时长、低置信触发人审比例、bad case 重复率、渠道材料复用率、POC 推进率。

### 14. 你能接受不是纯产品、需要往前台走吗？

**我的答案**：

可以，而且这也是我现在希望放大的方向。

我还是希望保留产品判断能力，但不想只停留在后端写需求。我更希望接触一线客户、销售和省公司的真实反馈，把客户问题翻译成产品能力、方案话术、行业模板和标准规则。

我理解贵司这个岗位不是让我单点冲上去交付所有客户，而是要搭体系、补角色、打通链路。这个方向和我过去做项目需求到标品、售前材料、POC 范围和交付边界沉淀是匹配的。

### 15. 你对运营商/国央企节奏适应吗？

**我的答案**：

我理解运营商和国央企体系里，产品推进不会只是快速做功能，还会涉及流程、权限、组织协同、合规、安全、渠道和长期运营。

我不追求每天换方向的刺激，更看重在稳定底座上把产品和业务长期做深。当然我也知道这类组织会有流程和协同成本，所以我希望发挥的是把复杂协同拆清楚、把规则定清楚、把材料和反馈闭环建起来，让事情真正落地的能力。

对我来说，中电信人工智能公司的吸引力也在这里：它不是只有 AI Demo，而是有集团级场景、政企客户基础和真实落地链路，能把 AI 能力进入办公、行业和企业经营流程。

### 16. 你觉得自己的匹配点和短板是什么？

**我的答案**：

匹配点我会说三点。

第一，我懂 AI Agent 产品化，不会把 AI 只讲成问答，而会拆知识源、工作流、输出结构、置信度、人审和 bad case。第二，我有 B 端平台化和方案经验，做过 0 到 1 产品底座、约 70% 定制需求标品化、10+ 份售前方案和 POC 交付协同。第三，我理解客户需求转产品方案的过程，能把复杂场景拆成能力矩阵、版本规划、交付边界和演示材料。

短板也有。我不是从电信 AI 平台内部成长起来的，对星辰产品矩阵、政企渠道打法、省专合作机制和公司现有定价策略，需要入职后快速补齐。另外我过去更多在工业/设施运维场景，对政务、教育、交通等行业模板需要继续学习。

我的补齐方式会很具体：先深用产品、读现有方案、跟销售和交付复盘典型项目，再选一个场景做方案包小闭环。我的优势是学习不是停留在看资料，而是会很快转成可复用的产品材料和验收标准。

## 场景题

### 17. 如果客户说想做一个政企智能体方案，你会怎么从需求到方案？

**我的答案**：

我不会一上来就问客户要什么模型，而是先把业务链路和交付边界拆清楚。

第一，明确业务场景，比如是政务材料审核、政策问答、热线辅助、知识库检索、跨系统办事，还是内部办公提效。第二，拆用户和决策链：一线使用者、业务负责人、信息化部门、安全合规、采购和领导层分别关心什么。第三，盘点数据和系统：已有文档、数据库、业务系统、权限体系、接口、数据更新频率和敏感等级。第四，设计最小闭环：用户输入什么，智能体查什么知识、调什么工具、输出什么结果，哪些地方要人工确认，结果写回哪里。第五，定义验收：样例问题集、正确召回标准、输出结构、人工修改量、响应时间、失败兜底和安全边界。第六，输出方案材料：产品架构、功能版本、部署方式、实施计划、交付清单、风险和报价组成。

这里最重要的是不要把 AI 讲成一个孤立能力，而是讲成能进入客户工作流、能被验收、能被持续运营的方案。

### 18. 如果让你设计星辰智能体的产品包装，你会怎么分层？

**我的答案**：

我会按照客户购买和交付决策来分层，而不是按照内部功能树简单堆版本。

第一层是个人/小团队 SaaS 版，强调低门槛创建智能体、标准模板、知识库问答、基础工作流和用量包。第二层是企业团队版，强调团队空间、权限管理、知识库治理、协作发布、用量统计和管理后台。第三层是行业方案版，面向政务、工业、教育、交通等场景，重点是行业模板、场景 Demo、标准知识库结构、POC 验收样例和交付手册。第四层是私有化/省专版本，重点是内网部署、数据不出域、权限审计、系统集成、运维监控、专属服务和安全合规。

这样分层的好处是，销售不是按功能点硬卖，而是按客户决策点来讲：个人看低门槛，企业看权限和协作，行业客户看模板和验收，私有化客户看安全和运维。

### 19. 如果让你把一个通用办公智能体推广到行业版本，你会怎么做？

**我的答案**：

我会先把通用能力和行业能力分开。

通用能力包括智能体创建、知识库、工作流、工具调用、权限、评测、发布和用量统计；行业能力包括业务对象、行业知识源、流程状态、验收指标和客户术语。推广到行业版本时，不应该每个客户重做一套，而是从高频场景里沉淀模板。

我会选 1 到 2 个可验证场景先跑，比如政企知识问答或材料审核。先定义标准 Demo、知识库结构、样例问题、输出格式、人审规则和 POC 验收表，再通过客户和渠道反馈迭代。等这个小闭环跑通后，再沉淀成行业方案包，包括场景说明、产品架构、部署方式、交付清单、常见异议和报价组成。

这个思路和我过去做定制转标品类似：不是拒绝客户差异，而是把差异分成配置项、行业模板和客户专属集成。

### 20. 如果研发、销售、交付对方案边界意见不一致，你怎么推进？

**我的答案**：

我会先把分歧从“谁说了算”转成“目标和边界怎么定义”。

第一步，明确客户目标和本期成功标准，比如这次 POC 到底验证智能体问答准确性、流程自动化、私有化部署，还是渠道演示价值。第二步，把需求拆成 P0/P1/P2：P0 是必须交付并可验收的闭环，比如数据源、权限、人审、输出结构和验收样例；P1 是增强体验和可配置能力；P2 是规模化运营和高级分析。第三步，给各方看风险和代价：研发看实现复杂度，销售看客户承诺，交付看现场边界，产品看长期复用。第四步，形成决策记录，把本期做什么、不做什么、后续观察什么写清楚。

我的角色不是替某一方说话，而是把模糊需求翻译成可实现、可销售、可交付、可复用的方案。

## 反问准备

### 21. 最后你准备反问什么？

**我的答案**：

我会根据现场时间选两到三个问题。

第一，关于目标：这个岗位前 90 天最希望解决的问题是什么？是产品能力包装、某个行业方案、渠道材料，还是私有化交付方案？

第二，关于指标：团队现在判断产品解决方案经理做得好，主要看客户线索转化、POC 推进、渠道复用率、方案交付质量，还是产品 Roadmap 贡献？

第三，关于协作边界：这个岗位和研发产品经理、售前、渠道、运营、交付之间怎么分工？产品方案需要定义到功能版本、报价结构和验收口径吗？

第四，关于星辰智能体主线：未来半年更优先做平台通用能力升级，还是沉淀政务、工业、教育、交通等行业模板？

如果只能问一个，我会问：

> 这个岗位前 90 天最希望我交付的可见成果是什么？这样如果有机会加入团队，我可以更快把工作产出对齐到团队最需要的地方。

## 临场提醒

- 不要只说“我做过什么”，每题都补一句“为什么这样判断”。
- 不要堆很多项目，核心项目就打 Inspector Agent，一个项目讲深比讲广更适合二面。
- 不要虚构 AI 上线效果、收入结果或模型训练职责。没有的数字就说成验收指标或可补齐路径。
- 每个开放题最后都要落回中电信：星辰智能体、SaaS/私有化、行业方案、省公司/渠道、交付验收。
- 压力题用固定结构：承认边界 -> 讲已有可迁移经验 -> 给补齐路径 -> 回到岗位价值。
