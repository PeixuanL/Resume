# 博锐尚格｜快速学习与技术协作（口语素材）

> 用途：被问“你怎么证明学习能力”“你如何进入陌生技术/行业”“技术能力到什么程度”时使用。
>
> 原则：不把快速学习当抽象性格标签；每次都落到“短时间进入什么问题、产出什么、如何验证”。

## 1. 主回答：你怎么证明自己快速学习？（40 秒）

我不太想把快速学习只说成“我学得快”，我更看重能不能尽快形成可交付的东西。现在这份工作里，我刚进入数字孪生和设施运维场景时，需要同时接手两条产品线；我先通过产品演示、已有资料和和研发/交付同学的沟通理解运行逻辑，第二周就参与了版本演示。之后接触新的设施运维场景，我在一个月内把需求收敛成 MVP 范围，和团队形成了可以演示和继续验证的方案。

我后来做 Booking 的 Coding 和 POC 也是同一种方式：先把业务对象、状态和异常路径讲清楚，再通过实现去验证。对我来说，快速学习不是先把所有知识学完，而是先建立问题框架、找到关键资料和专家，再用一个小的可验证产出来校正理解。

## 2. Unity / C# 是什么证明？（30 秒辅助例子）

我在研究生项目里有过一个比较典型的技术学习经历。当时为了实现 AR 交互和 AI 图像生成相关功能，我用大约一个月集中自学 Unity 和 C#，重点先解决 UI 交互和 AR 功能，然后做了十多个测试程序，把 AI 图像生成和材质附着跑起来。中间我还针对一段相关代码做过改写，原作者后来采纳了这个修改。

这段经历不能证明我现在是 C# 工程师，但能证明我进入陌生技术时，会先围绕一个具体功能学习、快速做原型、在实践里定位问题，而不是只停在看课程。

## 3. 如果被问：你不会 Python，为什么仍能做这个岗位？（谨慎版）

Python 不是我当前最深的工程栈，我不会把自己说成能替代研发做模型或后端开发。但我不是完全脱离技术地做产品：我有 Unity/C# 的自学和原型实践，也在近期用 AI 辅助完成过 Booking 模块的 Coding、部署和 POC 验证。

这些经历让我比较清楚，产品侧需要先定义什么：数据从哪里来、字段和状态怎么组织、接口失败怎么处理、AI 输出什么、怎么验收。具体到 Python，我会按岗位实际场景去补，比如数据清洗、接口调用或验证脚本；我的优势是能快速把业务问题转成可实现、可测试的需求，再和研发一起推进，而不是把自己包装成算法工程师。

## 4. 如果被问：你进入陌生的机电/运维知识时怎么学？（30 秒）

我会先从用户任务和业务对象进入，而不是先背设备原理。比如先弄清一条告警来自哪个设备和测点、影响哪个空间和系统、现场人员原来怎么判断、要查哪些 SOP 和历史记录；涉及具体故障机理或安全边界时，再和机电或运维专家确认。这样我能先把专业知识变成产品需要的字段、流程、界面和验收条件，也不会越过专业判断的边界。

## 5. 自我提醒

- 主证据优先：当前工作的一周/一个月形成可交付产出 + Booking POC。
- Unity/C# 是辅助证据：证明学习方法，不作为“会 Python”的替代证明。
- 不说“我什么都能很快学会”；说清学习目标、路径、可交付物和边界。
- 若没有被问 Python，不主动展开这段，把时间留给 Inspector 和岗位方向判断。
