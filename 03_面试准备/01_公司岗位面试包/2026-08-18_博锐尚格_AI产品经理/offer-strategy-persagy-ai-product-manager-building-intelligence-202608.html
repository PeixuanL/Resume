Story bank3. 需要强化的真实故事

STORY 01 · 主故事 · 一稿多用

Inspector 设施运维 Agent：从告警到工单

可证明：AI 产品设计、Agent/RAG、业务对象建模、研发协作、业务测试、风险边界。

S/T：客户已有告警、设备台账、工单、SOP和历史记录，但告警之后仍需人工查资料、判断原因和组织处置。你的任务是把 AI 嵌入告警到工单的主流程，而不是做独立聊天框。

A 必须讲清：你如何定义告警理解、知识检索、诊断、方案和工单草稿的职责；如何规定输入输出、依据、置信度、缺失信息、人工确认、异常路径和回写。

R 只用已确认口径：MVP覆盖海外标杆客户80%+高优先级诉求，形成可复用的设施运维产品底座，支撑部分项目实施周期从5–6个月缩短到1–2个月；不要说成AI已大规模全量上线。

核心落点：我做的不是让模型回答得更像专家，而是把它拆成研发能实现、测试能验收、客户能理解的业务闭环。

STORY 02 · 结果故事

多客户需求转标品：约70%定制需求沉淀

可证明：需求调研、优先级、平台化、客户差异抽象、交付效率和产品 owner 判断。

重点结构：客户需求为什么分散 → 你如何区分客户偏好、共性能力和项目专属集成 → 如何沉淀资产、告警、工单、3D沙盘、SOP和交付基线 → 结果与复盘。

不要只报70%。必须补一个真实代表需求、一次取舍和一个没有做进首期的项目边界。

STORY 03 · 技术权衡故事

日本建工 POC：异形构件、碰撞、限高、载重和重力模拟

可证明：复杂场景拆解、客户需求翻译、研发协作、技术边界和 POC 成功标准。

必须压到2分钟：先说客户要验证什么，再说你把场景收敛成哪些可验收点，最后说穿模/重力效果等技术限制下如何做短期权衡，避免讲成8分钟的技术漫游。

STORY 04 · 技术学习补强

Unity/C# 与快速进入复杂产品

可以证明：快速学习复杂技术系统、读懂技术约束、把学习结果变成原型/Demo/产品产出。

边界：这能支持“我能快速学习 Python 并用于产品验证”的说法，但不能单独证明“熟练掌握 Python”。最好的表达是：你过去通过 Unity/C#、数字孪生和复杂产品快速建立技术语境，并形成了可交付产出；现在把同样方法用于 Python 数据处理和 AI 验证。

STORY 05 · 反馈迭代故事

Predictor4. 高概率问题与准备方向

Q1 你做的 Inspector Agent 和我们建筑空间智能产品有什么关系？

准备：不要说“完全一样”。说两者共同处理工程对象、设备/空间上下文、告警/异常、知识检索、处置建议和结果回写；你的迁移点是产品闭环和验收方法。

Q2 你具体负责了 Agent 哪些部分？研发做了什么？

准备：产品负责场景卡片、输入输出、Agent职责、知识源、状态、人工边界、测试脚本和验收；研发负责模型、服务、接口和工程实现。

Q3 如何验证 AI Agent 是否真的有用？

准备：设备识别、正确知识召回、引用正确、输出字段完整、低置信兜底、高风险人审、工单草稿可用、执行结果回写。

Q4 如果用户说 AI 建议太泛，你怎么处理？

准备：先分类是任务太大、知识缺失、检索不准、输出结构松还是流程缺输入，再分别收敛场景、补知识、调检索、收紧 Schema 或补字段。

Q5 你 Python 到什么程度？

准备：真实说明当前能用于产品验证/数据处理的程度；用 Unity/C# 快速学习案例证明迁移能力，并说明正在补 Python 小型数据处理、API和测试脚本。不要把 C# 基础阅读说成 Python 熟练。

Q6 你不是电气/暖通/自动化专业，如何理解建筑智能化？

准备：承认边界，强调建筑空间、系统关系和 B 端对象建模；补充 BMS/SCADA/EAM/IoT、设备告警、SOP和工单的产品层理解。

Q7 你只有约1.5年产品经验，为什么能胜任3–5年岗位？

准备：用三条产品线、11个版本、10+项目、0→1 Agent、约70%标品化和交付周期结果证明经验密度；不要泛泛说“学习能力强”。

Q8 为什么从建筑转产品，再转 AI？

准备：建筑理解空间和复杂约束，数字孪生把空间变成数据/对象，设施运维把对象放进运行流程，Agent进一步帮助诊断、推荐和沉淀。

Q9 如果让你做一个建筑设备诊断 Agent，你会怎么开始？

准备：先选一个高频、低到中风险、数据完整的设备/告警；盘点BMS/IoT、台账、SOP、历史工单；定义输出、人工确认、回写和历史案例验收。

Q10 你如何根据使用方反馈迭代 AI 产品？

准备：把反馈拆成知识缺失、检索未命中、知识过期、输出结构、数据质量、权限/流程和模型推理问题，避免笼统说“模型不准”。

这些问题来自本岗位 JD、禹数方向准备材料，以及你在中电信业务二面中暴露出的真实表达风险：回答过长、先铺背景、交付物说得晚、没有第一句先给结论。

Gap map5. 缺口怎么补，哪些不能假装补齐

🔧 Python：短期可补到“可验证”

准备一个真实小练习：读取一组告警/工单 JSON，清洗字段，调用一个 API 或 mock 接口，输出 bad case 汇总。面试能讲清输入、处理、异常和结果即可；没有做到之前不要写“熟练掌握”。

🔧 建筑机电：补产品层地图

画出“设备/点位→BMS或IoT→告警→空间→SOP→工单→结果回写”的图，补 HVAC、BMS/IBMS、EMS/FMS、BACnet、OPC UA、MQTT 的基本边界。

🟡 Agent验证：补一组可复用检查项

把 Inspector 的验收整理成一页：场景、输入、知识源、期望输出、风险等级、人工节点、通过条件和 bad case 类别。重点是证明你会验收，不是硬报准确率。

⏳ 年限：只能用经验密度防守

2年经验本身不能短期创造。准备一段不回避年限的回答，用多产品线、客户交付、标品化和复杂度证明你不是只做单点页面。
