# 博锐尚格二面准备：项目负责人 / 算法工程师面

## 一、先定主线

二面不要再把重点放在“我懂 Inspector、RAG、Agent、楼宇运维”上。一面已经验证过这些。

二面要证明的是：

> 我能把一个模糊的业务问题，拆成可用的数据、可检索的知识、可评测的 AI 输出和可交付的研发任务，并和算法工程师一起把质量闭环跑起来。

博锐尚格公开定位本身就是用数据智能连接建筑中的人、设备和空间，因此对方更可能关注建筑领域数据如何沉淀为上层 AI 可用的知识与服务，而不只是一个聊天入口。参考：[博锐尚格官网](https://www.persagy.com/)。

## 二、主要准备方向

### 1. 数据到知识的生产链

准备清楚一条完整链路：

`业务问题 -> 数据源 -> 对象与字段 -> 清洗/标准化 -> 知识加工 -> 专家审核 -> 发布/版本 -> 检索或调用 -> 反馈与修订`

重点不是背术语，而是能回答：

- 信息来自哪些系统，谁是可信来源？
- 设备、空间、人员、工单、SOP 之间如何关联？
- 知识如何标记适用范围、版本、时间和来源？
- 内容变更后如何审核、发布、回滚？
- 专家不愿意手工录入时，如何用 AI 先生成草稿再让专家确认？

### 2. AI 输出质量与坏案例分析

这是最应该补的一块。要能把“回答不准”拆开，而不是笼统说继续优化模型。

至少分成：

- 找不到：知识库没有、检索召回不到、关键词/实体没有对齐
- 找错了：召回内容不相关、过滤条件或权限不对、版本冲突
- 说错了：模型超出证据推断、引用不支持结论、格式不完整
- 数据错了：资产关系、设备 ID、空间关系或实时状态不一致
- 流程错了：工具调用失败、参数错误、权限不足、写回失败
- 体验问题：延迟高、结果太长、没有给出下一步动作

准备一张坏案例表，字段包括：用户问题、上下文、期望答案/证据、实际输出、错误类型、影响等级、可能原因、改进动作、验证结果。

### 3. 评测设计

算法负责人很可能会问：你怎么判断检索或回答变好了？

你的回答要体现“先建立样例和标准，再谈优化”：

- 选取真实、典型、高风险问题，覆盖正常、边界和容易出错的场景
- 为每条问题定义标准答案、必须引用的证据和不可接受的回答
- 区分检索质量与生成质量，不把“回答流畅”当成“回答正确”
- 关注实体识别、召回相关性、证据覆盖、事实正确、结构完整、拒答合理性、延迟和成本
- 通过离线评测集观察版本变化，再用线上反馈和人工抽检发现新坏案例

如果被要求先做 MVP，可以说：先选一个业务域、一个任务、一个知识来源和一种输出格式，建立最小评测集与人工确认环节，再扩展范围。

### 4. 产品和算法的协作边界

要能说清楚你不是替算法调参数，但也不是把问题丢给算法。

产品负责：任务定义、用户和风险、输入输出、数据/知识边界、样例与验收标准、优先级、反馈机制。

算法负责：检索/排序/模型方案、特征或提示策略、训练与服务实现、性能和资源评估。

双方共同负责：错误定位、方案取舍、指标权衡、上线门槛和迭代节奏。

可用的协作表达：

> 我会先把问题变成可复现的样例和验收标准，再和算法一起判断是数据问题、检索问题、生成问题还是流程问题。这样讨论的是证据和指标，不是“模型感觉不太好”。

### 5. Python 和数据动手能力

不需要把自己包装成开发，但要能证明可以处理真实的小任务。重点补：

- 读取和校验 JSON、CSV
- 按设备、工单、问题类型聚合坏案例
- 调 API 并处理异常、超时和返回字段缺失
- 用简单脚本对比两版结果，输出通过率和错误分类
- 看懂基础的数据结构、字段映射和日志

不要只说“会用 Python 辅助工作”。准备一个真实可演示的小例子：输入一批问答结果，按错误类型统计，并输出一张复盘表。没有做过的部分直接说目前能做到的边界。

### 6. 项目负责人视角

项目负责人可能更关心你能不能把事情往前推：

- 需求不清、数据不齐时，如何先定义最小交付？
- 算法效果达不到预期时，如何判断降目标、换方案还是补数据？
- 领域专家和研发意见不一致时，依据什么决策？
- 多个业务方同时要需求时，如何排优先级？
- 你如何让一个知识生产工具被专家真正使用？

回答时少讲“沟通协调”，多讲你会产出什么：任务定义、数据字典、样例集、评测表、问题单、版本记录和上线验收结果。

## 三、可能出现的新问题

这些问题和你已经准备过的 Inspector、Agent、RAG 基础题不是一回事，优先准备思路即可：

1. 如果让你接手知识检索模块，前两周会先看什么、产出什么？
2. 你怎么搭一条从原始资料到可检索知识的生产流程？
3. 没有历史评测数据时，怎么建立第一版评测集？
4. 检索召回率不错，但最终回答仍然错误，你怎么定位？
5. 如何区分数据问题、实体关联问题、检索问题和模型生成问题？
6. 知识库里存在旧版本和新版本冲突，你如何处理？
7. 领域专家不愿意维护知识库，你怎么降低维护成本？
8. 算法同学说目标指标和当前资源不匹配，你怎么推进？
9. 如果只能做两周，你会砍掉哪些范围，保留哪条闭环？
10. 你如何判断一个 AI 能力已经达到上线门槛，而不是只能演示？
11. 你会怎样利用 Python 帮研发或自己分析一批坏案例？
12. 作为项目负责人，你如何处理一次跨团队推进不顺或方案调整？

## 四、还要补充的材料

### 必补

- 一张“数据源 -> 标准对象 -> 知识 -> 检索 -> AI 输出 -> 人工反馈”的图
- 一张 AI 坏案例分类与评测表
- 一个 Python 小练习：读取结果、分类错误、统计通过率
- 一个能体现跨角色推进的项目故事，讲清背景、判断、动作、结果和复盘

### 有时间再补

- 召回、精确、重排、引用正确性、结构化输出、拒答的基本含义
- 知识版本、来源追溯、权限和敏感信息控制
- 延迟、模型调用成本、人工审核成本之间的取舍
- 结构化数据和非结构化文档如何共同支持检索

## 五、面试时的定位句

> 我不是算法工程师，但我能把业务任务转成算法可验证的问题：先定义对象、数据源、输出、风险和黄金样例，再联合研发定位坏案例，判断优先改数据、检索、生成还是流程。我的优势是把行业场景、产品交付和质量验收串成一个闭环。

## 六、不要主动重复的内容

Inspector 产品定义、告警到工单链路、RAG 基础输入、Agent 与规则、人工确认边界、楼宇场景判断、已有项目介绍、Python 是否会写、为什么做 AI 产品等，一面已经覆盖。除非对方从数据、评测或研发协作角度追问，否则只做一句背景带过。

## 七、高概率问题：做 AI 遇到过什么卡点

这个问题很可能出现。不要只讲困难和结果，要按“卡点 -> 定位 -> 取舍 -> 当前状态/下一步”回答。

### 主故事：告警输入与误报处理还不够成熟

建议用下面这种更接近真实面试的说法：

> 当时我们在设计一条从设备告警到工单的 AI 链路，最开始的想法比较直接：系统收到告警后，让 AI 判断原因、推荐处理方案，再生成工单。真正往下梳理以后，我发现难点不在于把模型接上，而在于告警本身的信息不够完整。单独看一条告警，通常只能知道哪个设备出现了什么异常，但还缺少它所在的空间、上下游关系、历史记录和对应的 SOP。直接让模型给结论，答案可能听起来很完整，但不一定有足够证据。
>
> 所以后来我把方案边界往前收了一步：先把告警、设备和空间关系、历史记录、SOP 这些信息组织起来，让 AI 输出诊断理由、依据、缺失信息和处理建议，再生成工单草稿，由人确认后进入后续流程。这样做并不是说误报问题已经解决了，而是先避免模型在证据不足时直接驱动工单。项目当时主要处在方案和 POC 阶段，告警接入和信息聚合是先完成的部分，误报治理还没有形成完整的线上闭环。后续我会优先做同一设备、同一告警的重复聚合，再结合人工确认结果建立评测样例，区分到底是数据不足、关联错误、检索没找到，还是模型生成越界。
>
> 这件事对我最大的提醒是，AI 项目卡住时，不能只看模型本身。要先确认输入数据、知识来源和业务流程是否支撑这个结论，再决定是补数据、改检索、加人工确认，还是调整产品目标。

被追问时要补：

- 怎么判断是误报：看重复频率、设备状态、历史工单和人工确认结果
- 怎么控制风险：不给模型直接闭环执行，先生成建议和工单草稿
- 怎么验证改进：建立带标准答案/证据的样例，比较改动前后的错误类型

### 备用故事一：从演示效果到可落地能力

你可以讲 AI 方案需要接入真实告警、设备/空间关系、SOP 和历史记录，难点在于数据、权限、接口和人工流程要同时成立。这里要明确哪些是方案设计、POC 或协作落地，哪些还不是你独立负责的生产结果。

### 备用故事二：多源资产数据映射

Asset Hub 涉及表格、BIM 和其他来源，字段、命名和 ID 不一致，候选匹配不能完全自动确认。因此需要把候选结果、置信度和人工确认放在流程里，并维护跨系统 ID 映射。这个故事适合回答“数据质量/实体对齐卡在哪里”。

### 不建议这样回答

- “模型经常幻觉，后来调了 Prompt 就好了”
- “数据不够，所以没办法”
- 把未来规划说成已经上线的结果
- 只说沟通困难，不说具体卡在哪个输入、指标或流程节点

## 八、告警误报怎么处理

面试时可以按下面的顺序讲：

1. **先定义误报**：区分重复告警、阈值抖动、传感器异常、设备维护期间告警、上下文不匹配，以及确实有效但优先级较低的告警。不能把所有“用户觉得烦”的告警都当成误报。
2. **先做告警治理**：同一设备、同一告警 ID 在一段时间内重复出现时先聚合成一个事件；但如果严重程度变化、设备状态变化或已经恢复后再次发生，应生成新的事件。高风险告警不能因为聚合被隐藏。
3. **补充上下文**：关联设备、空间、上下游关系、实时状态、历史记录、维护状态和 SOP，让判断不只依赖一条告警文本。
4. **规则和 AI 分工**：重复聚合、阈值、权限和严重等级等确定性逻辑优先用规则；原因分析、相关历史检索和处理建议可以交给 AI，但必须展示依据和不确定信息。
5. **保留人工确认**：在数据和模型还不稳定时，AI 先给出告警解释、置信度、证据和建议，人工确认后再生成或关闭工单，并把确认结果沉淀为后续评测数据。
6. **评估不能只看误报率**：还要同时看漏报率、有效告警召回率、重复告警压缩率、人工确认耗时和高风险告警是否被及时发现。

口语版可以这样说：

> 我不会先简单调低告警阈值，因为这样可能减少误报，但也会带来漏报。我的处理顺序是先把重复告警、设备故障、维护期间告警和真正有效但低优先级的告警分开。对同一设备、同一告警在短时间内反复出现的情况，可以先聚合成一个事件，但如果严重程度或设备状态发生变化，还是要重新触发。然后再补充空间、上下游关系、实时状态、历史记录和 SOP。规则负责确定性的聚合和分级，AI 负责基于上下文做解释和建议，先保留人工确认。我们当时处在告警接入和信息聚合为主的阶段，所以误报治理还没有完整上线，我会把人工确认结果沉淀成评测样例，再分别判断是数据、关联、检索还是模型生成的问题。

## 九、二面反问与回答后的接法

反问不要连续问完就结束。对方回答后，用“复述理解 + 连接经历 + 表达贡献”回应 20 到 40 秒，再进入下一个问题。

### 1. 当前最希望解决什么问题

可以问：

> 您刚才提到团队在做知识生产、信息检索和 AI 输出质量分析。目前最希望优先解决的一个问题是什么？更偏数据质量、知识生产、检索效果，还是坏案例分析？

如果对方说知识不标准、数据比较散，可以接：

> 我理解现在的难点不是单纯把模型接进来，而是先让数据和知识变得可用。这和我做 Inspector 时的体会比较接近：设备、空间、历史记录和 SOP 如果没有关联起来，后面的 AI 输出很难稳定。如果有机会加入，我会先把一个具体场景的数据源、对象关系、知识结构和验收样例梳理清楚，再判断问题主要出在数据、检索还是模型。

如果对方说 AI 输出质量或坏案例较多，可以接：

> 这块我也比较感兴趣。我之前在告警到工单的方案里，误报治理还没有形成完整线上闭环，所以我不会把它说成已经解决过。但我会先把坏案例按数据缺失、实体关联、检索和生成错误拆开，再和算法一起判断优先改哪一层。

### 2. 入职前三个月的预期

可以问：

> 如果我加入，您希望我前三个月先交付什么结果，才算比较顺利？

对方回答后，可以接：

> 这个目标我能理解。按我的理解，前期可能不是马上做一个很大的 AI 产品，而是先选定一个具体场景，把问题、数据、知识、评测和交付流程跑通。我比较擅长把模糊需求拆成具体产物，比如数据字段、知识结构、样例集、问题清单和验收标准。

如果对方强调需要独立推动，可以接：

> 那我理解这个岗位不只是接需求，还要主动发现问题、排优先级和推动闭环。我过去做 Inspector 时也有类似情况，需要在多个定制需求里判断哪些能沉淀成标准能力。

### 3. 产品和算法的分工

可以问：

> 这个岗位和算法工程师通常怎么分工？产品经理需要参与到样例集、标注规则、评测指标和验收标准的什么程度？

对方回答后，可以接：

> 这和我的工作方式比较一致。我可以负责把业务任务、用户风险、输入输出、样例和验收标准定义清楚，也会参与坏案例分析；算法方案、模型选择和参数调优由算法同学负责，双方一起判断问题到底应该改数据、检索、生成还是流程。

如果对方提到需要产品自己处理数据或写脚本，可以接：

> 这部分我可以接受。我目前更适合用 Python 做 JSON、CSV、API 和结果分析这类小任务，帮助整理数据和定位坏案例。比较复杂的算法实现，我会和算法同学配合，不会把自己包装成算法开发。

### 4. 收口问题

时间允许时可以问：

> 结合今天的交流，您觉得我的经历最适合这个岗位的部分是什么？还有哪一块能力是我需要尽快补上的？

如果对方指出不足，可以接：

> 这个反馈我认同。尤其是您提到的这一点，我之前更多是在方案和 POC 阶段参与，完整线上评测经验还需要补强。如果加入，我会优先从具体场景、评测样例和坏案例闭环开始补起来。

整场反问问 3 个左右即可，优先顺序是：当前卡点、前三个月目标、协作边界。不要把已经问过的团队和产品线问题再问一遍。

## 十、根据二面补充信息重新校准

对方提到的重点是：信息标准化、查询准确性、查询数据分析、性能问题、查询架构和模型训练，以及话题元素。因此二面更偏查询基础设施和算法协作，准备主线应调整为：

`用户问题 -> 话题元素/实体抽取 -> 信息标准化 -> 召回/检索 -> 排序 -> 结果生成或返回 -> 日志分析/评测 -> 模型和数据迭代`

### 1. 信息标准化

要能说明如何统一：

- 同义词、别名、缩写和不同业务口径
- 实体、属性、时间、空间、设备等话题元素
- 字段、标签、枚举值和上下游 ID
- 原始数据、标准数据和展示数据之间的映射

不要只说“建立数据字典”，还要说清楚标准由谁维护、冲突如何处理、版本如何管理、标准化错误如何被发现。

### 2. 查询准确性

把“查得准”拆成几层：

- 是否正确理解用户意图
- 是否正确抽取话题元素和实体
- 是否召回了相关信息
- 排序结果是否把最相关内容放在前面
- 最终答案是否被证据支持

如果效果不好，先看日志和样例，判断是问题理解、实体对齐、标准化、召回、排序还是生成环节的问题，而不是直接说换模型。

### 3. 查询数据分析

准备说明会关注哪些数据：查询量、零结果率、低相关结果、重复查询、用户改写、点击/采纳、人工纠正、响应时延和不同话题元素的错误分布。

建议准备一个分析闭环：抽取一批真实查询 -> 按问题类型和错误类型分组 -> 找代表性坏案例 -> 判断根因 -> 提出数据、检索、模型或产品改动 -> 用同一评测集复测。

### 4. 性能问题

产品经理不需要主动讲底层优化细节，但要能定位查询链路：问题解析、标准化、召回、重排、模型调用、外部接口和结果拼装分别耗时多少。

可讨论的取舍包括：缓存、预计算、索引、减少召回范围、控制 TopK、分层模型、异步处理，以及准确性、延迟和成本之间的平衡。

### 5. 查询架构与模型训练

不要把自己包装成负责模型训练的人。你的准备重点是：

- 产品如何定义训练任务和目标
- 什么样的查询、标准答案、正负样本和坏案例可以用于训练或评测
- 如何设计标注规则，避免不同人理解不一致
- 如何区分训练集、验证集和独立测试集
- 模型更新后如何做回归评测和上线验收

可以这样定位：

> 我不负责算法模型本身的训练实现，但我可以把查询任务、话题元素、标准化规则、样例、坏案例和验收指标定义清楚，并和算法一起判断问题是补数据、改召回排序，还是调整模型训练。

### 6. 建议反问一个澄清问题

> 您提到的“话题元素”，目前主要是指查询中的实体、属性、时间和空间等结构化要素，还是已经有一套业务主题和标签体系？现在最大的误差更集中在元素抽取、标准化对齐，还是后面的召回和排序？

这个问题可以帮助你判断对方当前更需要的是知识/数据产品能力，还是查询评测和算法协作能力。
