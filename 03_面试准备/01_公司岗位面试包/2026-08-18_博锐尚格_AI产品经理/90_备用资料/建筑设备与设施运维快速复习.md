# 建筑设备与设施运维快速复习

> 用途：准备“AI产品经理-B端（建筑空间智能方向）”面试。
> 复习目标：具备用产品经理视角理解建筑设备、告警、运维数据和 AI 闭环的能力。
> 使用方式：先看「一页速记」，再按面试官追问展开。

## 一页速记

建筑空间智能产品的核心关系是：

```text
空间 / 楼层
  → 设备系统
  → 设备与测点
  → 状态与告警
  → 诊断与处置建议
  → SOP / 工单
  → 现场执行与验收
  → 结果回写与经验沉淀
```

面试中要能回答五个问题：

1. 告警来自哪个设备或测点？
2. 设备属于哪个空间和系统？
3. 诊断还需要查询哪些上下文？
4. 什么结果可以生成工单，什么动作必须人工确认？
5. 执行结果如何回写到历史工单、SOP 或知识库？

## 一、建筑设备知识

### 1. 暖通设备

重点理解设备之间的关系，不要求展开工程原理。

| 设备 | 产品视角下的作用 | 常见关联数据 |
|---|---|---|
| 冷水机组 | 制冷系统核心设备 | 出回水温度、压力、流量、运行状态、故障码 |
| 冷却塔 | 向外部环境释放热量 | 风机状态、水温、风机频率、补水状态 |
| 水泵 | 输送冷冻水或冷却水 | 启停状态、频率、流量、压力、电流 |
| AHU 空气处理机组 | 处理和输送空气 | 送回风温度、湿度、风机状态、阀门开度 |
| 风机盘管 FCU | 末端房间的空气调节 | 室温、设定温度、阀门状态、风机档位 |
| 阀门 | 控制水路或风路流量 | 开度、开关状态、故障状态 |
| 传感器 / 测点 | 提供设备运行数据 | 温度、压力、流量、湿度、电流、电压、振动 |

可以用这条简单链路理解暖通问题：

```text
空间温度异常
→ 查看末端设备状态
→ 查看阀门 / 风机 / 水泵
→ 查看冷源与管路相关设备
→ 查询历史告警、维修记录和 SOP
→ 给出检查项或生成工单草稿
```

### 2. 电气和高风险设备

重点不是背设备结构，而是理解风险和人工确认边界。

| 设备 / 系统 | 需要理解的产品问题 |
|---|---|
| 变压器、配电柜 | 电压、电流、温度、过载、跳闸、相序等异常如何形成告警 |
| UPS、发电机 | 供电切换、剩余容量、运行状态、故障和维护记录 |
| 电梯 | 告警与安全风险相关，诊断建议需要人工确认 |
| 消防系统 | 高风险告警不能由 AI 直接执行处置动作 |
| 强电设备 | AI 可以辅助检索、判断和生成检查项，现场操作需要授权人员确认 |

产品表达重点：

> AI 可以提供告警解释、证据、可能原因和下一步检查项；涉及消防、电梯、强电等高风险设备时，输出应进入人工复核和审计流程。

## 二、建筑运维系统

| 系统 | 可以理解成 | 常见数据 |
|---|---|---|
| BMS / IBMS | 建筑设备监控与综合管理系统 | 设备状态、告警、控制点、运行参数 |
| FMCS | 厂务设施监控系统，常见于复杂工业或洁净厂房 | 环境、机电、工艺相关设备和告警 |
| SCADA | 工业现场监控与数据采集系统 | 实时点位、控制状态、报警和历史曲线 |
| EAM / CMMS | 资产和维修管理系统 | 资产台账、维护计划、维修工单、备件和历史记录 |
| EMS | 能源管理系统 | 电、水、气、冷量、能耗趋势和能效指标 |

面试中可以用“数据分工”来回答：

```text
BMS / FMCS / SCADA：设备正在发生什么
EAM / CMMS：设备过去发生过什么、如何维护
EMS：能源消耗和效率如何变化
Inspector：把空间、设备、告警、工单和现场执行串起来
AI Agent：基于这些上下文辅助理解、诊断和处置
```

## 三、运维数据模型

### 1. 静态资产数据

- 设备名称、设备类型、品牌、型号
- 所属建筑、楼层、空间和系统
- 设备唯一 ID
- 上下游设备关系
- 安装时间、保修期、关键备件
- 设备说明书、图纸、维护手册

### 2. 动态运行数据

- 运行 / 停止 / 离线状态
- 温度、压力、流量、湿度
- 电压、电流、功率、频率
- 振动、转速、阀门开度
- 数据时间戳、采样周期、单位和数据质量

### 3. 告警数据

- 告警名称和描述
- 告警来源、设备、测点和空间
- 告警类型、等级和触发时间
- 当前状态：未响应、已确认、已指派、已处置、已关闭等
- 触发值、阈值、恢复时间
- 外部系统 ID、原始报文或扩展 JSON
- 是否已关联工单、关联哪张工单

### 4. 工单和执行数据

- 工单来源：告警、手动、外接系统、巡检、预防性维护等
- 工单对象：设备、位置、系统、关联告警
- 负责人、计划时间、优先级、SLA
- 检查步骤、执行结果、异常说明
- 照片、视频、文本、读数和参考资料
- 实际根因、处理动作、备件、验收结果
- 退回、改派、升级、审计和回写记录

## 四、可靠性和维护方法

### FMEA

面试中先掌握这条关系：

```text
设备 / 部件
→ 故障模式
→ 故障原因
→ 故障影响
→ 检测方式
→ 预防或处置措施
→ 实际结果与经验回写
```

FMEA 和 Inspector 的连接点：

- 告警可以触发故障模式识别
- 设备和历史工单可以提供原因与证据
- SOP 可以提供检查和处置步骤
- 工单执行结果可以验证原有判断
- 审结结果可以反哺 FMEA、SOP 和知识库

### 三种维护方式

| 类型 | 触发方式 | 产品关注点 |
|---|---|---|
| 故障维修 | 设备已经发生异常 | 告警、诊断、派单和快速处置 |
| 预防性维护 | 按周期或计划执行 | 计划、周期、设备范围和 SOP |
| 预测性维护 | 根据趋势或算法预测风险 | 预测依据、置信度、检查建议和人工确认 |

## 五、AI 产品追问框架

当面试官给出一个建筑设备场景，可以按下面顺序展开：

### 1. 识别场景

- 谁发现问题？值班人员、主管还是系统？
- 是单点告警、组合告警还是能耗异常？
- 影响哪个空间、系统和设备？

### 2. 补充上下文

- 查设备台账和上下游关系
- 查实时曲线和历史趋势
- 查历史告警和维修工单
- 查 SOP、手册、图纸和备件
- 查人员、权限、计划和现场条件

### 3. 设计 AI 输出

- 现象摘要
- 可能原因 TopN
- 每个判断的依据
- 置信度和缺失信息
- 建议检查项
- 推荐 SOP
- 工单草稿字段
- 是否需要主管或专家确认

### 4. 设计闭环

```text
告警理解
→ 上下文检索
→ 诊断辅助
→ 方案生成
→ 工单草稿
→ 人工确认
→ 现场执行
→ 验收与结果回写
```

### 5. 设计验收

- 设备和位置关联是否正确
- 告警与工单关联是否正确
- 诊断依据是否可追溯
- 工单字段是否完整
- 建议步骤是否可执行
- 高风险场景是否触发人工复核
- 执行结果是否能回写
- bad case 是否能分类和复盘

## 六、面试时的产品判断句

可以围绕以下关键词展开，不需要主动讲完整设备原理：

> 我会先确认告警对象、设备、空间、所属系统和测点，再补充实时数据、历史工单、SOP 和上下游关系。AI 输出不仅要给结论，还要给依据、置信度、缺失信息和下一步检查项。若需要生成工单，应先映射到标准工单字段，由人工确认后进入派发和执行；高风险设备则保留强制人工复核、权限和操作留痕。

## 七、30 分钟快速复习顺序

1. **5 分钟**：背熟“空间 → 系统 → 设备 → 告警 → 工单 → 回写”。

## 八、系统集成记忆框架

系统集成面试可以固定按五层回答：

### 1. 对象和 ID

- 资产：`assetId`
- 设施 / 空间：`facilityId`
- 设备：`deviceId`
- Twin / BIM：`twinId`、`bimObjectId`
- BMS：`bmsDeviceId`、`bmsPointId`
- 工单：`workOrderId`
- 预约与控制：`bookingId`、`controlPlanId`
- 请求追踪：`requestId`、`correlationId`

### 2. 数据归属

```text
Asset Hub：静态资产台账
Twin：运行态属性语义和当前值
DFS / 数据平台：历史数据与分析集
BMS / IBMS：实时状态与控制执行反馈
工单系统：任务执行、维修结果与验收记录
```

### 3. 数据流转

```text
读取来源
→ 字段映射
→ 格式标准化
→ ID 关联
→ 完整性校验
→ 人工确认
→ 写入或展示
→ 状态反馈
→ 审计留痕
```

### 4. 集成可靠性

- 幂等：同一请求重复发送，不重复创建工单或控制计划
- 重试：网络失败、超时、BMS 拒绝时支持再次处理
- 冲突：多端修改时明确生效版本和处理人
- 部分失败：设备级失败不能被整体成功覆盖
- 版本：编辑控制计划或预约后生成新版本，保留旧版本记录

### 5. 权限和安全

- 租户、项目和设施范围隔离
- 普通用户、管理员、运维人员、集成账号分权
- 高风险动作二次确认
- 请求、响应、操作人、时间和原因可追溯

## 九、近期项目故事补充

### 1. Asset Hub / Inspector 实施平台

**定位**：资产治理、实施交付和数据基线故事。

**S｜背景关键词**

- 客户资料来自 Excel、BIM、业务系统等多个来源
- 字段口径不统一，存在重复、缺失和冲突
- 后续 Twin、3D、DFS、Inspector 需要稳定的资产基线

**T｜任务关键词**

- 明确 Asset Hub P0 边界
- 建立导入、字段映射、候选确认、冲突处理、版本审计和导出闭环
- 区分资产台账、运行态数据、历史数据和跨系统绑定

**A｜动作关键词**

- 设备作为核心资产对象
- 空间、系统作为台账维度和内部关系
- 定义原始记录、字段映射、资产候选、冲突和正式台账版本
- 区分 Asset Hub 静态属性、Twin 运行态属性、DFS 历史数据
- 通过 API 草案、Mock、前端、后端领域模型和测试验证产品闭环

**R｜结果关键词**

- 形成纯资产台账 P0 产品边界
- 形成导入、映射、候选、冲突、审计和导出模型
- 形成可运行前端、API 草案、Mock 和独立后端骨架

**L｜复盘关键词**

- 实施平台首先要解决“哪份数据可信、谁确认、哪一版可交付”
- 资产台账、运行数据和跨系统绑定不能混成一个对象
- AI 可辅助字段识别、映射建议和冲突提示，但关键确认需要证据链

### 2. HSA 资产管理

**定位**：建筑设备、BMS/BIM 和资产数据流故事。

**核心链路**

```text
BMS / BIM / 文件资料
→ Data Fusion 清洗标准化
→ 资产台账与 ID 关联
→ 资产详情、3D 位置、BMS 页面、运行状态、告警和趋势
```

**需要记忆的关键词**

- 设备、空间、系统、BIM 对象和 BMS 点位
- 资产 ID、BMS 设备 ID、BIM 对象 ID、点位 ID
- 资产主数据、运行数据、历史数据的归属差异
- 数据读取、匹配、补全、冲突确认和可选回写
- BMS 是否允许写入、同步频率、页面跳转和数据来源优先级

### 3. HSA Facility Booking

**定位**：建筑空间、设施预约、BMS/IBMS 控制计划和状态反馈故事。

**核心链路**

```text
空间 / 设施
→ 预约规则与可用性校验
→ Booking
→ Control Plan
→ BMS / IBMS 同步
→ 接收 / 拒绝
→ 设备执行成功 / 失败
→ Dashboard、日志和审计回写
```

**STAR 关键词**

- S：预约不仅是表单，还涉及审批、容量、时间冲突和设备动作
- T：定义预约、控制计划、BMS 状态、失败处理和审计边界
- A：设计 `facilityId`、`deviceId`、`bookingId`、`controlPlanId`；区分 BMS accepted 和 execution success；设计 rejected、timeout、manual handling、权限、重发和幂等
- R：完成预约到控制计划、模拟下发、执行反馈、Dashboard 回写和 POC 验收闭环
- L：集成 POC 先验证对象、状态和边界，再推进真实接口

**表达边界**

- 当前 POC 使用 mock/seed 数据和模拟 BMS 状态
- 可以讲产品边界、状态机、数据模型、交接和验收
- 真实 BMS/IBMS 接口属于后续交付阶段
