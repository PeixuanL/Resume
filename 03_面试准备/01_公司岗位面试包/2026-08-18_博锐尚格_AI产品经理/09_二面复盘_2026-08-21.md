## 2. 本场面试的实际问答主线

### 2.1 开场和经历匹配｜约 02:10 起

你延续了一面使用的三条主线：

1. Inspector 设施运维底座从 0 到 1 的设计和迭代；
2. 围绕告警到工单的 AI 产品化设计；
3. 项目需求转成通用能力或配置能力。

自我介绍里提到了 Inspector MVP 覆盖海外客户 80% 以上的高优诉求，以及约 70% 定制需求沉淀为标品化能力。内容和岗位相关，但信息密度偏高，后面又展开了三条产品线和数字孪生底座，开场主线没有尽早收住。

更适合二面的定位句是：

> 我过去主要做的是把建筑空间里的设备、资产、告警和工单组织成可交付的 B 端产品，再把 AI 放进诊断、检索和工单草稿这些具体任务里。现在这段经历可以继续往应用层数据、语义关系和 AI 输出质量延伸。

### 2.2 数字孪生底座、资产台账和 ID 关系｜约 04:00—10:20

面试官重点确认你在数字孪生底座里的具体职责。你的回答主要包括：

- 真实设备、资产台账、3D 设备对象和空间信息之间的绑定；
- 客户原始表格导入、字段整理和资产基线建设；
- 设备 ID、点位 ID、资产 ID、空间 ID、3D 对象 ID 之间的映射；
- 通过 ID 关系表让 3D 场景、资产台账、点位数据和后续业务模块相互定位；
- 根据真实业务场景反向提出数字孪生平台 API 和能力优化要求。

这一段是本场比较有说服力的部分。你没有把资产治理说成抽象的数据中台，而是讲了数据从哪里来、对象怎么绑定、业务上为什么需要反向查找。

事实边界：你负责的是业务对象、字段关系、产品流程和平台能力要求，不是数据库、接口或底层数据同步实现。

### 2.3 语义层和 MVP 取舍｜约 10:20—12:25

面试官进一步问了语义关系是否需要持续扩充，以及有没有为了 MVP 做过妥协。

你回答了：

- MVP 阶段先覆盖设备位置和空间关系等基础关系；
- Demo 中还存在设备控制关系、上下游关系等更复杂的语义；
- 因为时间紧，部分关系先用已有关系支撑可视化展示；
- 后续在资产管理平台中再细化不同控制关系和上下游关系。

这个例子本身是有效的，因为它体现了范围取舍。但以后需要明确说出一句：

> 这种临时映射只服务 Demo 的展示和业务验证，不应作为生产语义标准；进入正式数据层前，必须把关系类型重新定义清楚。

录音转写将相关术语识别成 `Haslocation`、`Face`、`DTC control`、`Briskeema/Briskyma` 等，正式写材料时应确认准确名称。这里大概率涉及 `hasLocation`、设备控制关系以及 Brick Schema，但不要把转写错误直接当成正式术语。

### 2.4 AI 工具使用案例：Booking 模块｜约 12:50—16:05

面试官让你具体讲一个使用 AI 工具完成产品工作的例子。你讲的是设备/空间预约和 BMS 控制的 Booking 模块，内容包括：

- 整理项目原始需求和业务边界；
- 用 AI 辅助检索竞品和基础功能清单；
- 梳理用户旅程、系统内部流程和与 BMS 的数据流；
- 让 AI 生成初版 PRD 和前端原型；
- 你自己检查主流程、跳转、异常条件、编辑条件和边界逻辑；
- 由于真实资产 API 和 BMS 接口尚未接入，先使用 Mock 数据和模拟成功/失败结果；
- 预留资产接口和 BMS 下发接口，再完成前后端补齐、测试和部署；
- 当前更接近 Demo/内部验证阶段，真实 BMS 对接仍在后续。

这段证明了你能用 AI 提高产品设计和验证速度，也证明你理解“控制计划被接收”不等于“设备已经执行成功”。

风险在于：你花了较多时间描述“AI 生成了什么”，而不是先说明你做了哪些产品判断。下次可以压缩成：

> AI 负责资料整理、流程初稿和页面原型，我自己负责需求边界、状态设计、异常条件、接口预留和验收。因为真实 BMS 尚未接入，第一版用 Mock 数据验证流程，Demo 已完成部署，但不能把它说成真实设备控制已经上线。

### 2.5 Inspector 的 AI Agent 方案｜约 16:35—22:50

这是本场最长的一段深挖。你讲的完整链路是：

```text
告警触发
→ 获取设备、空间、告警描述、运行状态和历史记录
→ 生成可能原因、证据和缺失信息
→ 人工审核诊断方向
→ 检索当前有效 SOP、设备手册和相似历史工单
→ 生成候选处置方案
→ 人工选择和确认
→ 生成带设备、位置、优先级和步骤的工单草稿
→ 一线人员按步骤执行并补充结果
```

你还讲到了几个比较好的产品判断：

- AI 输出不能只有原因，还要有判断依据；
- 缺少设备位置、部件信息或运行数据时，要提示信息缺口；
- SOP 有适用场景、设备范围、版本和标签；
- 历史工单是参考案例，不能直接替代当前有效 SOP；
- 高风险判断和工单下发仍需要人工确认；
- 工单草稿要把前面已经确认的信息带入，减少一线人员重复填写。

这部分和博锐尚格当前的知识生产、语义层和查询质量方向贴合度最高。

需要修正的是阶段边界。Inspector 的真实底座是资产、告警、3D 场景和工单等产品能力；AI 诊断、方案生成和工单 Agent 在当前材料里更适合表述为产品方案、原型/Demo 和 POC 路径。不要让“设计了几个 Agent”“可以生成三个方案”“工单执行结果沉淀知识”等表达听起来像长期线上运营结果。

### 2.6 固定查询工具还是 Agent 自己查询｜约 22:52—23:47

这是本场最明显的薄弱点。

面试官实际上在问：如果给 Agent 一组查询能力，它是从固定查询接口中选择，还是自己生成查询并组合数据？你回答自己不太了解具体实施，由研发负责，产品侧定义业务标准、检索范围和输出格式。

这个边界没有问题，但少了一层产品判断。更完整的回答应该是混合方式：

> 确定性强、权限敏感、风险高的数据走固定 API 或工具，Agent 负责识别意图、抽取设备和空间等话题元素，再选择合适工具。需要组合分析的场景，可以允许它在受控工具清单里生成查询参数，但不让它自由访问底层数据。产品侧定义工具输入输出、必填条件、不可查询范围、标准样例和验收口径；算法和研发负责查询生成、路由和性能优化。

这段是下一轮必须练熟的回答。

### 2.7 你交给研发什么，如何验收｜约 23:50—26:50

面试官继续追问产品与研发的协作产物。你回答会定义：

- Agent 在什么场景触发；
- 需要哪些输入，包括告警、设备、空间和历史记录；
- 哪些数据需要前置调取；
- SOP 的来源、适用设备、版本、标签和检索范围；
- 输出需要包含原因、证据、缺失信息、执行度和下一步动作；
- 以 HVAC 温度告警为例，定义正确的设备、故障类型和应召回的 SOP；
- 研发实施后，你根据同一组标准验收，并按设备查错、资料缺失、标签不精准等原因定位 bad case。

这里已经具备较好的产品—算法协作雏形。下一步需要补成更标准的交付包：任务定义、对象和字段表、工具输入输出、黄金样例、正负样例、错误分类、验收阈值和回归方式。

## 3. 面试官透露出的岗位真实重点

你反问当前产品最需要优先解决什么问题后，面试官明确介绍了以下内容：

### 3.1 现有数字孪生平台缺少语义层

团队正在把数字孪生平台上的设备、设施、业务节点和数据对象连接起来，让原因、过程和结果能够被查询和关联。语义层不是单纯增加字段，而是让不同对象之间的关系可理解、可查询、可复用。

### 3.2 查询准确性和用户意图识别

目前已经有一些固定查询能力，但实际用户的问题表达不统一，有些问题不是单次查询，而是需要综合分析。团队希望 AI 能判断用户真正想查什么，再把问题转成合适的查询或分析任务。

### 3.3 数据分析和话题元素

有些分析可以提前计算或预处理，不应等用户提问后再临时调用多次模型。团队还在建设话题元素、对象和分析结果的积累能力。

### 3.4 性能和模型训练

面试官提到一个问题可能触发 8—10 次模型调用，响应时间可能达到几十秒甚至更长，因此性能是现实问题。同时，部分语义层内容可能需要专门模型或针对性训练。

### 3.5 入职前三个月

面试官提到，前期更需要业务侧的人参与查询准确性和数据分析，而不是只有研发推进。具体重点包括：

- 提高查询和意图识别准确度；
- 参与复杂故障或业务问题的数据分析；
- 把已有语义、对象和分析能力转成业务可用的查询结果；
- 和研发一起减少不必要的模型调用，改善响应速度。

这说明岗位的落点比“设计一个 Agent”更靠近“语义数据产品 + 查询质量 + 算法协作”。

## 4. 本场表现较好的地方

### 4.1 能把抽象数据问题讲成业务关系

你没有只说“做了数据治理”，而是讲了资产 ID、点位 ID、空间 ID、3D 对象 ID 和业务模块之间的关系。这是算法负责人或项目负责人比较容易认可的产品表达。

### 4.2 有真实的 MVP 取舍意识

你承认 MVP 阶段的语义关系不完整，也说明了为什么先用简化关系支撑 Demo，再在资产管理平台里继续细化。这个例子比“我会平衡业务和技术”更有证据。

### 4.3 AI 不是孤立聊天入口

你一直把 AI 放在告警诊断、处置方案和工单草稿里，并且保留人工审核。这和建筑运维场景的风险边界比较匹配。

### 4.4 能说明 AI 工具的真实使用边界

Booking 案例里，你讲清了 Mock 数据、接口预留、真实 BMS 尚未接入和后续对接计划，没有把 Demo 直接说成真实设备控制结果。

### 4.5 反问带出了岗位信息

你问了数据质量、查询效果和 bad case 等问题，促使面试官进一步说明语义层、查询准确性、数据分析、模型调用性能和前三个月目标。这是有效的反问。

## 5. 主要风险和改进点

### 5.1 开场过满

开场同时放了三条产品线、数字孪生底座、设施运维、AI 和标品化，信息量太大。二面开场控制在 60 秒左右，只保留：

> 复杂 B 端对象关系 + AI 任务流程 + 数据/知识质量。

### 5.2 AI 方案和真实交付阶段要分层

以后固定使用三层说法：

- 已有产品能力：资产、告警、3D 场景、工单和部分平台能力；
- 已完成方案/Demo/POC：AI 诊断、知识检索、方案生成、工单草稿；
- 尚待验证：长期准确率、采纳率、误报率、处理时长和模型线上收益。

### 5.3 不能只把查询架构交给研发

不需要负责模型或查询引擎实现，但产品侧至少要能定义：查询任务、话题元素、工具边界、输入输出、权限范围、黄金样例和验收标准。

### 5.4 语义妥协需要补“何时回收”

你讲了 Demo 阶段用简化关系，但还可以补一句：什么时候必须回收临时关系？判断标准是什么？例如进入正式数据层、影响查询结果、跨项目复用或需要被 AI 解释时，就不能继续使用展示性替代关系。

### 5.5 离职原因可以更短

本场回答真实，但花的时间略长。建议压成：

> 我目前还在职，过去两年主要积累了数字孪生、设施运维和 AI 产品化经验。最近公司经营和工作稳定性出现变化，所以开始看机会。我的前提仍然是方向匹配，希望继续在建筑空间、设备数据和 AI 应用层做深；这个岗位正好把已有领域经验延伸到语义层、查询和输出质量。

## 6. 下一轮只需要准备的四个问题

### Q1：固定工具/API 和 Agent 自由查询怎么选？

准备混合架构回答：高风险和确定性任务走固定工具；Agent 做意图识别、实体抽取和工具选择；组合分析在受控工具范围内生成参数；研发负责实现，产品负责任务、边界和验收。

### Q2：查询准确性怎么评估？

不要只说“回答是否正确”，拆成：

- 用户意图是否识别正确；
- 设备、空间、时间和对象是否抽取正确；
- 是否选择了正确工具；
- 查询结果是否完整、相关；
- 综合分析是否有依据；
- 是否出现零结果、错对象、错版本或无依据推断；
- 响应时间和模型调用次数是否可接受。

### Q3：入职前三个月会交付什么？

可以准备：

> 前两周先选一个高频查询场景，梳理对象、语义关系、现有工具、真实问题和错误样例；第一个月建立一组可复现的查询评测集，区分意图、实体、工具、结果和生成问题；后续和研发一起选一个优先问题做改动，用同一组样例回归，并同时看准确性、响应时间和人工修正原因。

这是一套计划性表达，不能说成已经在博锐尚格完成过。

### Q4：你交给算法/研发的具体产物是什么？

准备列出：

- 业务任务和触发条件；
- 对象、字段、语义关系和数据来源；
- 工具/API 输入输出和权限范围；
- 真实问题、黄金答案和负样例；
- bad case 分类和优先级；
- 验收阈值、回归方式和上线边界。

## 7. 一句话复盘

这场二面证明了你能把建筑空间里的复杂对象、数据关系和 AI 业务流程讲清楚；下一步要把“我设计了 Agent”继续收紧成“我能把用户问题拆成语义元素、受控查询、可验证结果和研发任务”，这样才更贴近对方当前真正要招的人。
