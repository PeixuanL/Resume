# AI 学习 Day 4：产品经理如何定义 Agent 的输入、输出和边界

> 今日目标：你不需要会写 Agent 代码，但要能像 AI 产品经理一样，把一个 Agent 功能讲成研发可实现、测试可验收、业务可使用的产品方案。

---

## 1. 今天先记住一句话

> Agent 的产品设计，不是写一句“AI 自动诊断告警”，而是定义清楚它能拿到哪些输入、要产出什么结果、哪些动作必须人工确认、失败时怎么兜底。

换成更直白的话：

```text
输入 = Agent 能看见什么
输出 = 业务能接住什么
边界 = AI 不能越过什么
```

如果这三件事没定义清楚，研发就不知道接哪些系统，测试也不知道怎么验收，业务方更不知道 AI 的结论能不能信。

---

## 2. 为什么“输入”很重要

AI Agent 不是凭空变聪明。它能不能诊断，取决于它能拿到什么上下文。

在设施运维告警诊断里，常见输入包括：

| 输入 | 作用 | 产品经理要定义的问题 |
|---|---|---|
| `alert_id` | 锁定是哪一条告警 | 告警类型、等级、触发时间、持续多久 |
| `device_id` | 锁定是哪台设备 | 设备型号、位置、责任人、维保周期 |
| 实时/历史时序数据 | 看异常是否持续或扩散 | 取近 10 分钟、24 小时，还是 7 天 |
| 历史工单 | 查类似问题怎么处理过 | 按设备、故障类型、空间区域怎么检索 |
| SOP / 厂商手册 | 给出处置步骤依据 | 哪些文档可用，版本是否有效 |
| 空间与设备关系 | 判断影响范围 | 上下游设备、同区域设备是否关联异常 |
| 用户角色与权限 | 控制 Agent 能调用什么 | 运维人员、主管、管理员权限不同 |

面试表达：

> 我会先定义 Agent 的输入边界。比如诊断告警时，最少需要 alert_id、device_id、告警类型、设备台账、近一段时间的时序数据、历史工单和 SOP。没有这些上下文，AI 只能给泛化建议，不能形成可验证的诊断结论。

---

## 3. 为什么“输出”更像产品交付物

AI 输出不能只是“可能是冷却水阀异常”。这句话看起来像诊断，但业务无法直接执行，也无法验收。

更合格的输出结构应该是：

```text
1. 可能根因 Top 3
2. 每个根因的判断依据
3. 置信度
4. 影响范围
5. 建议检查项
6. 关联 SOP / 历史案例
7. 缺失信息
8. 下一步动作入口
```

例子：

```text
可能根因：冷却水阀异常或管路局部堵塞。
判断依据：B3 空调机组温度过高与近 10 分钟冷却水流量下降同时出现；历史工单中同区域发生过冷却水阀卡滞；当前设备缺少最近一次阀门维护记录。
置信度：中。
影响范围：B3 空调区域，可能影响局部办公区温控。
建议检查项：检查阀门开度、管路压力、过滤器状态。
缺失信息：缺少现场阀门状态和管路压力读数。
下一步：人工确认后生成维修方案草稿。
```

面试表达：

> 我不会把 AI 输出设计成单句结论，而会要求它输出结构化结果：可能根因、判断依据、置信度、影响范围、建议动作和缺失信息。这样一线人员能判断该不该采纳，研发能落字段，测试也能按字段验收。

---

## 4. 为什么“边界”决定这个 AI 能不能上线

设施运维是高风险业务，尤其涉及电梯、消防、强电、暖通主机等设备。AI 可以辅助判断，但不能无限制自动操作。

需要定义三类边界：

| 边界类型 | 设计原则 | 示例 |
|---|---|---|
| 决策边界 | AI 给建议，人做决定 | AI 可以推荐检查冷却水阀，但不能直接判定必须停机 |
| 操作边界 | 高风险动作必须确认 | 派发工单、停机、扣减库存、导出报告要人工确认 |
| 知识边界 | 没依据时不能硬答 | 检索不到 SOP 或历史案例时，提示信息不足 |

面试表达：

> 我会把 Agent 定义成辅助决策系统，而不是自动替人决策。低风险场景可以给建议和草稿，高风险场景必须升级主管或专家；正式派发工单、停机、导出数据等动作都要人工确认，并保留操作审计。

## 5. 用 PRD 方式拆一个 Agent 功能

功能名称：

```text
AI 告警诊断
```

用户角色：

```text
运维经理、一线技师、值班主管
```

触发方式：

```text
用户在告警列表或设备详情页点击“AI 诊断”。
```

输入数据：

```text
alert_id、device_id、告警类型、设备台账、近 24 小时 BMS / IoT 数据、近 90 天历史工单、关联 SOP、用户角色权限。
```

Agent 动作：

```text
1. 解析告警对象、空间位置和告警等级。
2. 检索设备台账、历史工单和 SOP。
3. 关联同区域、同系统、上下游设备是否有并发异常。
4. 生成可能根因、依据、置信度、建议检查项和缺失信息。
5. 根据风险等级判断是否允许进入方案草稿。
```

输出结果：

```text
可能根因、判断依据、影响范围、置信度、建议检查项、关联资料、缺失信息、下一步操作。
```

人工确认点：

```text
用户确认诊断后，才能进入“制定维修方案”。
用户确认维修方案后，才能生成或下发工单。
高风险设备必须由主管确认。
```

异常与降级：

```text
知识库无结果：提示缺少资料，只输出通用检查方向。
设备数据缺失：提示数据源异常，不输出确定根因。
置信度低：只输出候选方向，不推荐自动方案。
工具调用失败：保留失败日志，并提示用户手动处理。
```

验收标准：

```text
1. 用户点击告警后，系统能正确带入 alert_id 和 device_id。
2. Agent 输出必须包含根因、依据、置信度、建议动作和缺失信息。
3. 低置信度场景不能输出确定结论。
4. 高风险设备不能自动下发工单。
5. 每次诊断和工具调用都有审计记录。
6. 用户修改或驳回 AI 建议后，系统能记录反馈。
```

## 6. 今天的自测题

### 题 1：为什么 Agent 需要输入定义？

参考答案：

> 因为 Agent 的诊断质量取决于它能获取的上下文。产品经理要定义清楚 alert_id、device_id、设备台账、历史工单、SOP、时序数据和用户权限等输入，否则 AI 只能给泛化建议，研发也不知道应该接哪些数据源。

### 题 2：为什么 AI 诊断结果要结构化？

参考答案：

> 结构化输出才能被业务流程接住。只输出一句“可能是阀门异常”无法验收，也无法生成工单；如果输出根因、依据、置信度、影响范围、建议检查项和缺失信息，一线人员可以判断是否采纳，系统也能进入下一步方案和工单流程。

### 题 3：为什么不能让 Agent 自动派发所有工单？

参考答案：

> 因为设施运维涉及安全、责任和现场不确定性。AI 可以生成工单草稿，但正式派发前需要人工确认；消防、电梯、强电等高风险场景还要主管或专家复核。这样既利用 AI 提效，又避免错误建议直接变成现场操作风险。

---

## 7. 今日可背面试答案

> 如果让我设计设施运维 Agent，我会先从产品边界拆，而不是只写“AI 自动诊断”。第一，定义输入，包括告警 ID、设备 ID、设备台账、时序数据、历史工单、SOP 和用户权限，确保 Agent 是基于业务上下文回答。第二，定义输出，要求结果包含可能根因、判断依据、置信度、影响范围、建议检查项和缺失信息，方便一线人员判断，也方便系统生成后续方案和工单。第三，定义边界，高风险动作必须人工确认，低置信度不输出确定结论，所有工具调用都要有权限和审计。这样 AI 才不是一个聊天框，而是能嵌入告警到工单流程的可交付能力。
