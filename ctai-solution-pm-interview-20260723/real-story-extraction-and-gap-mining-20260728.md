## 2. 故事卡 S1：Inspector 设施运维 Agent 闭环

### 能打的问题

- 讲一个你做 AI Agent 或 AI 产品化最有代表性的项目。
- 你怎么定义一个智能体产品？它和 Chatbot 有什么区别？
- RAG 怎么设计？怎么判断召回和回答准确？
- 你没有底层模型训练经验，为什么能做 AI 产品？
- 客户说智能体不稳定、不可信，你怎么排查？

### STAR 骨架

**S 背景**
设施运维场景中，客户不是没有系统，而是告警、设备台账、空间位置、SOP、历史工单等信息分散。一线人员看到告警后，需要人工查资料、问专家，再判断是否派工。

**T 你的任务**
你的任务不是做一个聊天入口，而是把 AI 嵌入“告警到工单”的业务闭环，定义 Agent 在什么节点介入、需要哪些上下文、输出什么、什么必须人工确认、怎么验收。

**A 关键动作**

- 拆业务流：告警理解 -> 上下文检索 -> 诊断建议 -> 处置方案 -> 工单草稿 -> 人工确认 -> 结果回写。
- 拆知识源：实时告警/传感器/设备状态、设备台账/空间位置、SOP/厂商手册、历史工单。
- 拆 Agent 职责：告警理解、RAG/知识检索、诊断输出、方案生成、工单草稿。
- 定义输出结构：可能原因、判断依据、置信度、缺失信息、建议动作、人工确认标记。
- 和研发对齐字段、接口、输出 Schema、异常路径、验收脚本和 bad case 分类。
- 明确边界：高风险动作不自动派发，AI 只生成建议或工单草稿，必须人工确认。

**R 结果**
这段 AI 能力是产品侧方案验证、Demo/POC 和可交付规划，不包装成模型训练或大规模全量上线。它证明你能把“大模型诊断”拆成研发能做、测试能验、客户能理解、现场人员敢用的产品闭环。商业结果要归因于整个设施运维产品 / Inspector 底座产品化：本地材料可讲设施运维产品 / Inspector MVP 覆盖标杆客户 80%+ 高优诉求，并吸引 5+ 潜在客户接洽；不要说成 AI Agent 单独上线后的结果，也不要说成单次市场宣传直接带来的结果。

### 60 秒口述版

> 我会讲 Inspector 设施运维 Agent。这个项目的背景是，客户现场不是没有系统，而是告警、设备台账、空间位置、SOP 和历史工单分散。一线人员看到告警后，仍然要人工查资料、问专家，再判断是否派工。
>
> 我的工作不是做一个聊天入口，而是把 AI 放进告警到工单的主流程。我把链路拆成告警理解、上下文检索、诊断建议、处置方案、工单草稿、人工确认和结果回写；同时定义知识源优先级、Agent 职责、输出结构和人审边界。比如 AI 输出必须包含可能原因、依据、置信度、缺失信息和建议动作，高风险动作不能自动派发，只能生成草稿由人确认。
>
> 这段 AI 能力我会谨慎表达为产品侧方案验证、Demo/POC 和可交付规划，但它证明我能把一个很虚的“大模型诊断”拆成研发能做、测试能验、客户能理解、交付能承接的产品闭环。

## 3. 故事卡 S2：项目需求转标品

### 能打的问题

- 你说约 70% 定制需求转标品，具体怎么判断？
- 客户强势要求定制，但你判断不该做，怎么处理？
- 从通用办公智能体到行业版本，怎么沉淀行业模板？
- 你怎么在销售、客户和研发之间守住产品边界？

### STAR 骨架

**S 背景**
B 端大客户项目中，很多需求一开始以定制形式出现。若每个客户都单独开发，会导致交付周期长、版本割裂、后续难维护。

**T 你的任务**
把项目需求从“客户定制清单”转成“哪些进产品底座、哪些配置化、哪些作为行业包/客户专属”的判断和落地。

**A 关键动作**

- 横向拉通相似业务场景和历史需求清单，看哪些需求反复出现。
- 结合现有产品边界和竞品/行业能力做校准。
- 把需求分成三类：客户偏好、跨客户共性业务问题、产品定位冲突。
- 对客户偏好做配置项或模板；对共性能力沉淀为标准模块；对定位冲突回到真实痛点，提供替代方案或明确边界。
- 把需求沉淀为配置项、标准模板、实施基线、Demo 脚本、交付手册和 Roadmap。

**R 结果**
材料中可讲口径：围绕佛吉亚、头部运营商等大客，把告警可视化、复杂工单状态机、3D 沙盘基线等沉进 Inspector 底座；团队整体约 70% 定制诉求标品化；某运营商多期交付由 5-6 个月压到 1-2 个月。
注意：二面要说“约 70% 是产品化复盘口径，不是财务口径，也不是我个人独立贡献口径”。

### 60 秒口述版

> 我说的约 70% 定制需求转标品，首先不是财务口径，也不是说我一个人独立创造了 70% 结果，而是项目需求复盘里的产品化口径：一批客户诉求最终没有做成单客户代码，而是沉淀成标准能力、配置项、模板或产品规则。
>
> 我的判断方式是三类：第一类是客户操作偏好，比如字段、入口、命名、流程顺序，这类尽量配置化；第二类是跨客户共性能力，比如资产台账、设备关系、3D 空间定位、告警到工单、SOP 模板、人审，这类反复出现就进标准模块；第三类是和产品定位冲突的需求，我会回到真实痛点，看是否能用更符合平台架构的方式解决。
>
> 这个经验迁移到中电信，就是省公司和行业客户需求不能每个都重做一套，而要分成通用平台能力、行业模板、客户专属集成和暂不做项，最终沉淀成可复制方案包和验收标准。

### 临时口述版（仅可作框架，别当完整故事）

> 我过去虽然 title 是产品经理，但参与过产品上线和推广支持。比较典型的是，我们不是把二十多个功能全部堆给售前和市场，而是从客户痛点和可演示价值出发，筛出十个真正能打的推广点，再转成 Demo、视频、产品规格、方案素材和培训口径。
>
> 我在里面的作用是把内部功能翻译成客户能理解的价值：它解决什么痛点、适合哪个场景、演示怎么讲、交付边界是什么、客户常见问题怎么回答。这个经验迁移到星辰智能体，就是不能只讲模型、RAG、工作流这些技术模块，而要变成客户痛点、标准话术、Demo 脚本、部署条件、POC 验收和常见异议。

### 当前答案记录（待后续细化）

> 我过去做过产品迭代后的市场和项目团队赋能。比较典型的是 Designer 7.4，以及 Designer / Inspector 8.0、8.1 这些版本迭代。
>
> 当时产品能力更新很多，但我不会把功能清单原样交给市场，而是先判断哪些功能真的能转成客户价值。我的筛选标准主要看三点：第一，对客户 ROI 有没有明显帮助；第二，是不是过去无法实现的新场景；第三，能不能形成完整业务闭环。像一些简单交互优化，如果客户感知不强，我不会放到主卖点里；但如果是新增监控视频接入、新增模块、设施运维闭环能力，或者能明显提升项目实施效率的交互，我会重点提炼出来。
>
> 之后我会面向市场和项目团队做产品价值传递，同时提供实际软件操作演示视频，帮助市场理解真实产品能力。市场基于这些内容写公众号宣传文章时，我也会帮忙审核文案，避免只讲技术词或夸大能力，而是把功能表达成客户能理解的场景价值和实施边界。
>
> 这段经历让我意识到，产品经理不只是把功能做出来，还要把功能翻译成市场能讲、项目能交付、客户能理解的价值。这一点和中电信这个产品解决方案经理岗位很接近。

### 追问防守：你怎么筛选卖点

> 我不会按研发投入大小筛，而是按客户感知价值筛。比如一个功能虽然研发工作量很大，但如果只是内部体验优化、客户不容易感知，我不会把它作为主宣传点。反过来，如果一个能力能让客户从“只能看数据”变成“能看到场景、告警、视频、处置流程串起来”，或者能让项目团队实施效率明显提升，我会把它包装成主卖点。
>
> 我的判断标准是：客户是否愿意为它买单，销售是否能讲清，项目团队是否能交付，后续能否复用到多个项目。
### 追问防守：渠道/省公司不会讲智能体怎么办

> 我会先把这件事理解成赋能体系问题，而不是单次培训问题。过去在 Designer 7.4、Designer / Inspector 8.0/8.1 迭代后，我做过类似工作：面向项目经理、实施/交付、售前和市场团队做产品价值传递和设施运维实施流程培训。我的做法不是让大家背功能清单，而是把版本能力拆成几类资产：客户痛点、核心卖点、操作演示视频、实施流程、交付边界和宣传口径。
>
> 如果迁移到星辰智能体，我也会按这个思路做渠道和省公司赋能：第一，给他们 5 分钟能讲清的价值话术；第二，给标准 Demo 脚本和真实操作路径；第三，给 POC 前置条件和验收样例；第四，给常见异议和边界，比如哪些场景需要私有化、哪些动作必须人审、哪些效果不能夸大。这样渠道不是只会说“大模型很强”，而是能讲清客户为什么需要、怎么试、怎么交付、出了问题怎么兜底。

### 深挖优先级

高。因为这是中电信二面最大风险点：岗位很看 GTM、渠道、省公司、商业化规则。当前已有可用回答方向，后续优先补“具体新增闭环能力”和“市场/项目团队复用结果”。

- 结果能不能讲“转正式合同”，是否涉及客户名保密？
- 这个 POC 最终验收时客户最认可的是哪项能力：重力模拟、载重/限高、超限识别、碰撞检测，还是整体货物分配方案？

### 当前 STAR

**S** 日本头部建工企业 POC，需要验证异形建筑构件在货物堆放和卡车运输中的货物分配方案。这个场景不是简单 3D 展示，而涉及重力模拟、载重、限高测算、超限识别和货物摆放时的碰撞检测。B 端 POC 如果范围过散，很容易变成“什么都演示一点”，但不能证明客户最关心的物流装载和运输可行性。
**T** 你的任务是和售前一起把客户真实痛点收敛成可验证场景，定义 POC 范围、数据前置、成功标准和产品边界，让 POC 能成为后续正式交付/合同范围的依据。
**A** 你把验证重点收敛到异形构件货物分配相关能力：构件摆放是否发生碰撞、是否超出车辆限高/载重、重力/空间关系是否能支持合理堆放判断。过程中把客户需求拆成本期必须验证的核心闭环、可用替代方案覆盖的增强项、以及后续正式交付或二期范围，并和售前/研发/客户持续对齐边界。
**R** 本地材料可讲：该日本头部建工 POC 后续转入正式合同。面试中应谨慎表达为“我参与了 POC 范围和成功标准收敛，帮助 POC 结果映射到正式交付范围和里程碑”，不要把合同结果全部归因到个人。

### 当前可用回答

> 我理解 B 端 POC 最怕范围太大，最后什么都试一点，但没有一个闭环能证明价值。之前在日本头部建工企业相关 POC 中，客户核心关注的是异形建筑构件在货物堆放和卡车运输中的分配问题，不是简单看一个 3D 模型。这个场景要验证构件怎么摆放、会不会碰撞、是否超出车辆限高和载重，以及重力和空间关系是否支持合理堆放。
>
> 所以我会先和售前一起把客户真实痛点收敛成 1 到 2 个可验证场景，而不是把 Designer 的所有能力都演示一遍。然后提前写清数据前置和成功标准：比如需要哪些构件尺寸和车辆约束，验收时看碰撞检测、限高/载重识别、摆放方案是否能支撑客户判断。
>
> 过程中如果客户新增需求，我不会直接拒绝，而是分成本期必须验证的核心闭环、可以用替代方案覆盖的增强项、以及后续正式交付或二期范围。这样客户感觉需求被承接，但团队不会失去 POC 主线。这个项目后续转入正式合同，我会谨慎表达为：我参与了 POC 范围和成功标准收敛，让试点结果能映射到正式交付范围和里程碑。

### 深挖优先级

中高。它能补 GTM 的商业结果，但目前事实颗粒度不足。

## 10. 当前答案记录：商业化定价和竞品分析

### 可打问题

- 你没有独立负责定价，怎么做产品包装和定价？
- 如果让你给星辰智能体做版本分层，你怎么拆？
- 竞品分析你会怎么看？
- 你过去有没有类似经验？

### 当前可用答案

> 我会先说明边界：我没有最终拍板过价格，但产品经理可以提供定价前的结构化依据。尤其 B 端产品不是简单按功能数量收费，而是看客户到底买的是平台能力、业务场景、接入规模，还是交付服务。
>
> 我一般会先把价格拆成四层。第一层是基础产品能力，也就是客户买这个产品的基础门槛，比如账号、组织空间、权限、基础模块、标准数据看板、基础 3D 场景或标准工作流。这一层决定的是客户是否能开始用。第二层是接入规模。B 端客户成本往往和接入量强相关，比如接多少设备、多少点位、多少数据源、多少业务系统、多少知识库、多少用户账号，或者大模型产品里多少 token / API 调用量。接入规模越大，实施、运维和资源成本越高，所以适合作为价格阶梯。
>
> 第三层是高级能力或行业包。比如设施运维场景里，单纯资产台账和看板是一层；如果加上视频接入、告警到工单、SOP 模板、预测性维护、AI 诊断、移动端执行闭环，就是更高价值的行业方案包。客户不是为多几个按钮付费，而是为更完整的业务闭环和效率提升付费。第四层是实施和服务成本，比如私有化部署、客户现场数据治理、第三方系统接口、权限/审计要求、培训、运维支持、后续版本升级。这些不能都塞进标准 SaaS 价格里，否则会低估交付成本，所以要拆成实施服务、集成服务或私有化费用。
>
> 竞品分析我也会按这四层看，而不是只问别人卖多少钱。传统硬件/系统厂商可能基础价格高，但包含硬件、项目交付和行业经验；轻量 SaaS 工具价格低，但私有化、深度集成和行业模板弱；平台型产品可能 API 和用量灵活，但需要客户自己建设场景。我们要对比的是价值组合，不是裸价格。

### 迁移到星辰智能体

> 如果迁移到星辰智能体，我会建议至少拆四类包。第一是 SaaS 试用或个人/小团队版，重点是低门槛开通、标准模板、基础知识库、基础工作流和用量包。第二是企业团队版，重点是团队空间、账号权限、知识库治理、API/工具接入、用量统计、评测和运营看板。第三是行业方案版，面向政务、工业、教育、交通等客户，重点不是多给几个功能，而是提供行业模板、业务系统对接、POC 验收样例、安全合规材料和交付手册。第四是私有化/省专版本，重点是内网部署、数据不出域、权限审计、系统集成、运维监控和专属服务。
>
> 这四类价格不一定由我最终决定，但产品解决方案经理要先把客户购买理由、产品边界、交付成本和可复用程度拆清楚。这样销售和省公司出去讲的时候，不是说“我们有大模型和智能体”，而是能说明客户该买哪一版、为什么值、试点怎么验收、后续怎么扩展。

### 追问防守：你过去有没有类似经验

> 我过去没有独立做最终定价，但做过类似的价值和交付拆解。比如在设施运维产品里，我会把能力拆成基础底座、可配置模块、行业/项目场景和实施服务。基础底座包括资产、告警、3D 场景、工单这些通用能力；高级模块包括视频接入、设施运维闭环、AI 辅助诊断这类更强场景价值；实施服务则包括客户数据接入、现场配置、项目团队培训和交付边界确认。
>
> 这类拆解虽然不是最终报价，但会直接影响售前怎么讲方案、市场怎么包装卖点、项目团队怎么判断交付成本。我的价值是在定价前把客户为什么愿意付费和我们交付成本在哪里拆清楚。
